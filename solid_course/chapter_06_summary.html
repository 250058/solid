06. 종합: 도서관 대출 시스템

다섯 원칙을 한 도메인에 함께 적용하고, 어디서 멈춰야 하는지까지 판단하기

학습목표

  1. 하나의 도메인 코드에서 SRP·OCP·LSP·ISP·DIP 위반 지점을 찾아 해당 원칙 이름과 연결할 수 있다.
  2. 5원칙을 적용한 구조에서 새 요구(회원 유형 추가, 알림 수단 교체)가 어떤 클래스 추가·수정으로 흡수되는지 설명할 수 있다.
  3. YAGNI에 비추어 추상화를 지금 추가할지 미룰지 판단할 수 있다.

개념

지금까지 원칙을 하나씩 따로 배웠지만, 실제 코드에서 다섯 원칙은 서로 맞물려 작동합니다.

원칙한 문장이 장에서 답하는 질문
SRP (1장)클래스의 변경 이유는 하나영수증 양식이 바뀌면 대출 규칙 코드도 열어야 하나?
OCP (2장)확장에 열리고 수정에 닫힘회원 유형이 늘면 기존 코드를 고쳐야 하나?
LSP (3장)하위 타입은 상위 타입의 계약을 지킴새 정책 클래스가 서비스의 기대를 깨지 않나?
ISP (4장)클라이언트별 작은 인터페이스서비스가 쓰지도 않는 메서드에 의존하나?
DIP (5장)고수준·저수준 모두 추상에 의존저장소·알림을 바꾸거나 가짜로 테스트할 수 있나?

그리고 마지막으로 꼭 필요한 브레이크가 하나 있습니다.

📦 새 개념: YAGNI (You Aren't Gonna Need It)

  • 정의: "지금 필요하지 않은 기능·추상화는 만들지 않는다." 실제 요구가 생겼을 때 추가한다.
  • 왜 필요?: SOLID를 기계적으로 적용하면 바뀔 일이 없는 곳에도 인터페이스·팩토리·설정 로더가 쌓여 코드를 읽기 어렵게 만든다(과잉 설계). 미래 예측은 자주 틀리고, 틀린 추상은 없는 추상보다 고치기 어렵다.
  • 예: "나중에 DB를 바꿀지도 모르니" 지금 다중 DB 어댑터를 만들지 않는다. 대신 바꾸기 쉬운 구조(DIP)만 유지하고, 실제로 DB가 필요해지면 그때 구현 하나를 추가한다.

📦 새 개념: 팩토리 (Factory)

  • 정의: 조건(설정값, 회원 유형 등)을 보고 어떤 구현 객체를 만들지 결정해 돌려주는 함수나 클래스
  • 왜 필요?: 객체를 고르는 if를 한 곳에 모아, 쓰는 쪽은 구체 클래스 이름을 몰라도 되게 하려고. 단, 고를 구현이 하나뿐이면 군더더기다
  • 예: def make_notifier(kind: str) -> Notifier: return SmsNotifier() if kind == "sms" else EmailNotifier()

💡 핵심 포인트: SOLID와 YAGNI는 충돌하지 않는다

SOLID는 "이미 반복되고 있는 변경을 싸게 만드는 방법", YAGNI는 "아직 오지 않은 변경에 미리 돈을 쓰지 말라"는 경고입니다. 변경이 두 번째로 찾아왔을 때 원칙을 적용해도 대부분 늦지 않습니다.

상황

학교 도서관 대출 프로그램. 처음엔 학생(3권/14일)과 교사(10권/30일)만 있었고, 한 클래스 BeforeLibrary가 대출 규칙 판단, 기록 저장, 이메일 알림, 영수증 출력을 모두 처리했습니다.

새 학기가 되자 요구가 몰려옵니다.

  • "졸업생도 1권, 7일까지 빌릴 수 있게 해 주세요." (회원 유형 추가)
  • "영수증에 책 ID 말고 책 제목을 찍어 주세요." (출력 양식 변경)
  • "알림 로직 테스트할 때 진짜 메일이 나가지 않게 해 주세요." (알림 교체/테스트)

세 요구 모두 서로 다른 이유인데, 고칠 곳은 전부 checkout 메서드 하나입니다.

5원칙 적용 전

동작은 합니다. 하지만 [문제 N] 주석마다 어떤 원칙이 깨졌는지 붙여 두었습니다.

"""
6장. 종합: 도서관 대출 시스템에 SOLID 5원칙 함께 적용하기

목적:
    하나의 도메인(학교 도서관 대출)에서 SRP·OCP·LSP·ISP·DIP가 각각 어디에 쓰이는지,
    그리고 '어디까지만' 적용해야 하는지(YAGNI, 과잉 설계 경계)를 함께 보여 준다.

구성:
    1) 5원칙 적용 전: 모든 일을 혼자 하는 BeforeLibrary
    2) 5원칙 적용 후: 역할별로 나뉜 작은 클래스들 + 조립 지점(build_library)

실행 방법:
    python3 code/chapter_06_summary.py
"""

from abc import ABC, abstractmethod
from dataclasses import dataclass, field
from datetime import date, timedelta
from typing import Protocol


# =====================================================================
# 5원칙 적용 전: 한 클래스가 규칙·저장·알림·출력을 모두 떠안는다
# =====================================================================

class BeforeLibrary:
    def __init__(self) -> None:
        self.books: dict[str, str] = {"B1": "파이썬 입문", "B2": "객체지향의 사실과 오해"}
        self.loans: list[tuple[str, str, date]] = []  # (회원ID, 책ID, 반납 예정일)

    def checkout(self, member_id: str, member_type: str, book_id: str, today: date) -> None:
        # [문제 1: SRP 위반] 대출 규칙, 저장, 알림, 영수증 출력이 한 메서드에 섞여 있다.
        #   → 영수증 양식이 바뀌어도, 알림 수단이 바뀌어도, 대출 규칙이 바뀌어도 이 메서드를 연다.

        # [문제 2: OCP 위반] 회원 유형이 늘 때마다(졸업생, 외부인...) elif를 추가해야 한다.
        if member_type == "student":
            limit, days = 3, 14
        elif member_type == "teacher":
            limit, days = 10, 30
        else:
            raise ValueError("알 수 없는 회원 유형")

        current = sum(1 for m, _, _ in self.loans if m == member_id)
        if current >= limit:
            print(f"[거절] {member_id}: 대출 한도({limit}권) 초과")
            return

        due = today + timedelta(days=days)
        # [문제 3: DIP 위반] 저장소(내부 리스트)와 알림(print로 흉내 낸 이메일)에 직접 묶여 있다.
        #   → DB로 바꾸거나 SMS로 바꾸려면 업무 규칙 코드를 고쳐야 하고, 테스트용 가짜도 못 넣는다.
        self.loans.append((member_id, book_id, due))
        print(f"[EMAIL] {member_id}님, '{self.books[book_id]}' 반납일은 {due}입니다.")
        print(f"[영수증] {member_id} | {book_id} | ~{due}")
  • [문제 1] SRP: 규칙·저장·알림·출력이라는 서로 다른 변경 이유가 한 메서드에 모여 있습니다.
  • [문제 2] OCP: 회원 유형이 늘 때마다 elif를 추가해야 합니다. 실제로 졸업생 요구가 오자 ValueError가 납니다.
  • [문제 3] DIP: 저장소와 알림이 구현(리스트, print 이메일)에 직접 묶여 교체·테스트가 불가능합니다.

LSP와 ISP 위반은 이 코드에 직접 보이지 않습니다. 애초에 상속도 인터페이스도 없기 때문입니다. 두 원칙은 구조를 나누기 시작한 뒤 "나눈 조각들이 올바르게 맞물리는가"를 점검하는 원칙이라는 점을 기억하세요.

5원칙 적용 후

원칙마다 [해결 N] 표시를 따라가 보세요.

# =====================================================================
# 5원칙 적용 후
# =====================================================================

@dataclass(frozen=True)
class Book:
    book_id: str
    title: str


@dataclass(frozen=True)
class Loan:
    member_id: str
    book: Book
    due: date


# ---------------------------------------------------------------------
# [해결 2: OCP] + [해결 3: LSP] 회원 유형별 대출 정책
# ---------------------------------------------------------------------
class LoanPolicy(ABC):
    """대출 정책의 '계약'.

    계약(모든 하위 클래스가 지켜야 함):
      - max_books()는 1 이상의 정수를 돌려준다.
      - loan_days()는 1 이상의 정수를 돌려준다.
      - 예외를 던져 '대출 자체를 막는' 방식으로 계약을 바꾸지 않는다.
    → LoanService는 어떤 하위 정책이 오든 이 계약만 믿고 동작한다(치환 가능성, LSP).
    """

    @abstractmethod
    def max_books(self) -> int: ...

    @abstractmethod
    def loan_days(self) -> int: ...


class StudentPolicy(LoanPolicy):
    def max_books(self) -> int:
        return 3

    def loan_days(self) -> int:
        return 14


class TeacherPolicy(LoanPolicy):
    def max_books(self) -> int:
        return 10

    def loan_days(self) -> int:
        return 30


class GraduatePolicy(LoanPolicy):
    """요구 변경 '졸업생도 1권, 7일 대출 허용': 새 클래스 추가만으로 흡수(OCP).

    [LSP 주의] '졸업생은 대출 불가'를 표현하려고 max_books()에서 예외를 던지면
    부모 계약을 깨는 것이다. 그런 요구라면 정책이 아니라 회원 자격 검사에서 다뤄야 한다.
    """

    def max_books(self) -> int:
        return 1

    def loan_days(self) -> int:
        return 7


# ---------------------------------------------------------------------
# [해결 4: ISP] 클라이언트가 필요한 만큼만 아는 작은 인터페이스(Protocol)
# ---------------------------------------------------------------------
class BookFinder(Protocol):
    def find(self, book_id: str) -> Book: ...


class LoanRecorder(Protocol):
    def add(self, loan: Loan) -> None: ...
    def count_by_member(self, member_id: str) -> int: ...


class Notifier(Protocol):
    def notify(self, member_id: str, message: str) -> None: ...


# ---------------------------------------------------------------------
# 저수준 구현들 (세부 사항)
# ---------------------------------------------------------------------
class InMemoryCatalog:
    """BookFinder를 '구조적으로' 만족한다(상속 없이 find 메서드만 있으면 됨)."""

    def __init__(self, books: list[Book]) -> None:
        self._books = {b.book_id: b for b in books}

    def find(self, book_id: str) -> Book:
        return self._books[book_id]


@dataclass
class InMemoryLoans:
    """LoanRecorder를 만족한다. 나중에 DB 버전이 필요해지면 그때 같은 모양으로 하나 더 만든다."""

    loans: list[Loan] = field(default_factory=list)

    def add(self, loan: Loan) -> None:
        self.loans.append(loan)

    def count_by_member(self, member_id: str) -> int:
        return sum(1 for loan in self.loans if loan.member_id == member_id)


class ConsoleEmailNotifier:
    def notify(self, member_id: str, message: str) -> None:
        print(f"[EMAIL] {member_id}님, {message}")


class FakeNotifier:
    """테스트용: 실제로 보내지 않고 기록만 남긴다(DIP 덕분에 끼울 수 있음)."""

    def __init__(self) -> None:
        self.messages: list[str] = []

    def notify(self, member_id: str, message: str) -> None:
        self.messages.append(f"{member_id}:{message}")


# ---------------------------------------------------------------------
# [해결 1: SRP] 변경 이유별로 나눈 클래스
# ---------------------------------------------------------------------
class ReceiptFormatter:
    """변경 이유: '영수증 양식'이 바뀔 때만."""

    def format(self, loan: Loan) -> str:
        return f"[영수증] {loan.member_id} | {loan.book.title} | ~{loan.due}"


class LoanService:
    """변경 이유: '대출 업무 규칙'이 바뀔 때만.

    [해결 5: DIP] 저장소·알림·정책을 직접 만들지 않고 추상(Protocol/ABC)으로 주입받는다.
    → 이 클래스 안에는 InMemory..., ConsoleEmail... 같은 구현 이름이 한 번도 나오지 않는다.
    """

    def __init__(self, finder: BookFinder, recorder: LoanRecorder, notifier: Notifier) -> None:
        self.finder = finder
        self.recorder = recorder
        self.notifier = notifier

    def checkout(self, member_id: str, policy: LoanPolicy, book_id: str, today: date) -> Loan | None:
        if self.recorder.count_by_member(member_id) >= policy.max_books():
            print(f"[거절] {member_id}: 대출 한도({policy.max_books()}권) 초과")
            return None
        book = self.finder.find(book_id)
        loan = Loan(member_id, book, today + timedelta(days=policy.loan_days()))
        self.recorder.add(loan)
        self.notifier.notify(member_id, f"'{book.title}' 반납일은 {loan.due}입니다.")
        return loan


# [YAGNI] 일부러 만들지 않은 것들:
#   - 결제 플러그인 인터페이스, 다중 DB 어댑터, 정책을 읽는 설정 파일 로더 ...
#   지금 요구사항에 없고 변경이 반복된 적도 없다. 실제로 필요해지는 순간 위 구조에
#   클래스 하나를 더하는 것으로 충분하므로, 미리 추상화 층을 쌓지 않는다.


def build_library(notifier: Notifier) -> LoanService:
    """조립 지점(Composition Root): 어떤 구현을 쓸지는 여기 한 곳에서만 정한다."""
    catalog = InMemoryCatalog([Book("B1", "파이썬 입문"), Book("B2", "객체지향의 사실과 오해")])
    return LoanService(catalog, InMemoryLoans(), notifier)


if __name__ == "__main__":
    today = date(2026, 3, 2)

    print("=== 5원칙 적용 전 ===")
    before = BeforeLibrary()
    before.checkout("s01", "student", "B1", today)
    try:
        before.checkout("g01", "graduate", "B2", today)
    except ValueError as e:
        print(f"[오류] 졸업생 대출 불가 → 코드를 열어 elif 추가 필요 ({e})")

    print("\n=== 5원칙 적용 후 ===")
    service = build_library(ConsoleEmailNotifier())
    formatter = ReceiptFormatter()
    for member, policy, book in [
        ("s01", StudentPolicy(), "B1"),
        ("t01", TeacherPolicy(), "B2"),
        ("g01", GraduatePolicy(), "B1"),   # 새 정책: 기존 코드 수정 없이 추가
        ("g01", GraduatePolicy(), "B2"),   # 한도 1권 → 거절
    ]:
        loan = service.checkout(member, policy, book, today)
        if loan:
            print(formatter.format(loan))

    print("\n=== 가짜 알림으로 테스트 ===")
    fake = FakeNotifier()
    build_library(fake).checkout("s02", StudentPolicy(), "B2", today)
    assert fake.messages == ["s02:'객체지향의 사실과 오해' 반납일은 2026-03-16입니다."]
    print(f"기록된 알림: {fake.messages}")
    print("테스트 통과")

원칙별로 어디에 적용됐나

원칙적용 위치흡수하는 변경
[해결 1] SRPLoanService(대출 규칙) / ReceiptFormatter(영수증)영수증에 책 제목 찍기 → ReceiptFormatter만 수정
[해결 2] OCPLoanPolicy + StudentPolicy, TeacherPolicy졸업생 추가 → GraduatePolicy 클래스 추가, 기존 코드 무수정
[해결 3] LSPLoanPolicy docstring의 계약(1 이상 반환, 예외 금지)어떤 정책이 와도 LoanService가 분기 없이 동작
[해결 4] ISPBookFinder, LoanRecorder, Notifier 작은 Protocol서비스는 자기가 쓰는 메서드만 앎 → 저장소에 관리용 메서드가 늘어도 영향 없음
[해결 5] DIPLoanService.__init__ 주입 + build_library 조립 지점메일 대신 가짜 알림 → FakeNotifier 주입, LoanService 무수정

⚠️ 흔한 오해: "LSP를 지키려면 상속을 피해야 한다"

상속 자체가 문제가 아니라 계약을 깨는 하위 타입이 문제입니다. 만약 "졸업생은 대출 불가"를 구현하려고 GraduatePolicy.max_books()에서 예외를 던지면, LoanService가 정책 종류를 확인하는 if isinstance(...)를 다시 들여야 합니다. 그 순간 OCP도 함께 무너집니다. 원칙들이 맞물려 있다는 좋은 예입니다.

그리고 일부러 하지 않은 것 (YAGNI)

코드 하단 # [YAGNI] 주석을 보세요. 결제 플러그인, 다중 DB 어댑터, 정책 설정 파일 로더는 만들지 않았습니다. 요구도 없고 변경이 반복된 적도 없기 때문입니다. 필요해지면 지금 구조에 클래스 하나를 더하면 됩니다.

반대로 Book, Loan 같은 단순 데이터 클래스나 ReceiptFormatter에는 추상 클래스를 만들지 않았습니다. 구현이 하나뿐이고 교체할 이유가 없기 때문입니다.

실행: python3 code/chapter_06_summary.py

정리

요구 변경적용 전: 수정할 곳적용 후: 수정할 곳
졸업생 회원 유형checkout에 elif 추가GraduatePolicy 추가
영수증 양식checkout 안 print 수정ReceiptFormatter만
알림 교체·테스트checkout 수정, 테스트 불가새 Notifier 구현 + build_library

⚠️ 과잉 설계 경계: 이런 신호가 보이면 멈추세요

  • 구현이 하나뿐인 추상 클래스가 여러 개이고, 바뀐 적도 바뀔 계획도 없다.
  • 기능 하나를 따라가려면 파일 다섯 개를 열어야 하는데, 그 대가로 얻은 교체 가능성이 한 번도 쓰이지 않았다.
  • "나중에 혹시"가 설계 이유의 전부다.

판단 기준: 같은 이유의 변경이 실제로 두 번째 찾아왔는가? 외부 자원 경계(DB, 네트워크, 시간)처럼 테스트를 위해 대체가 꼭 필요한 곳은 예외적으로 처음부터 추상을 둘 만합니다.

다 읽었다면 종합 진단표로 자신의 이해 수준을 점검해 보세요.

이해 점검

Q1. [개념 확인] (학습목표 1)

BeforeLibrary.checkout의 if member_type == "student": ... elif member_type == "teacher": ... 분기가 가장 직접적으로 위반하는 원칙은?

  1. SRP
  2. OCP
  3. LSP
  4. ISP
정답: 2 (OCP)
새 회원 유형이 올 때마다 기존 메서드를 수정해야 하므로 "수정에 닫혀 있지" 않습니다.
왜 오답이 매력적인가: 1(SRP)도 메서드 전체로 보면 위반이지만, 그것은 규칙·저장·알림·출력이 섞인 문제이지 이 분기 자체의 문제는 아닙니다. 3(LSP)은 "회원 유형=타입"이라 떠올리기 쉽지만 여기엔 상속 계층이 없어 치환할 하위 타입도 없습니다.

Q2. [개념 확인] (학습목표 3)

YAGNI는 "추상 클래스나 인터페이스를 쓰지 말라"는 뜻이므로 SOLID와 정면으로 충돌한다. (O/X)

  1. O
  2. X
정답: X
YAGNI는 "지금 필요 없는 것을 미리 만들지 말라"는 뜻입니다. 이미 반복되는 변경(회원 유형 추가)이나 테스트에 필요한 외부 경계(알림)에 추상을 두는 것은 YAGNI와 충돌하지 않습니다.
왜 오답이 매력적인가: 두 개념이 "추상을 늘려라 vs 줄여라"처럼 정반대로 들리기 때문입니다. 실제로는 "언제" 추상을 만들지에 대한 서로 보완적인 기준입니다.

Q3. [위반 찾기] (학습목표 1)

누군가 아래 정책을 추가했습니다. 이 코드가 깨뜨리는 원칙은?

class SuspendedPolicy(LoanPolicy):
    def max_books(self) -> int:
        raise PermissionError("정지 회원은 대출 불가")

    def loan_days(self) -> int:
        return 0
  1. SRP
  2. ISP
  3. LSP
  4. DIP
정답: 3 (LSP)
LoanPolicy의 계약은 "1 이상의 정수를 반환, 예외로 대출을 막지 않음"입니다. 이 하위 타입은 계약을 두 번 깨뜨립니다. (1) max_books()가 정수 대신 PermissionError를 던져 "예외로 대출을 막지 않는다"는 약속을 깨고, (2) loan_days()가 0을 반환해 "1 이상"이라는 사후조건을 약화합니다. 둘 중 하나만 있어도 부모 자리에 넣었을 때 LoanService가 깨집니다.
왜 오답이 매력적인가: 4(DIP)는 LoanPolicy라는 추상을 상속했으니 문제없어 보이게 만듭니다. 추상에 의존하는 것과 그 추상의 계약을 지키는 것은 별개입니다. 정지 회원 처리는 정책이 아니라 대출 전 자격 검사(별도 책임)로 다루는 편이 맞습니다.

Q4. [위반 찾기] (학습목표 1)

저장소 Protocol을 아래처럼 하나로 합치자는 제안이 나왔습니다. LoanService 입장에서 어떤 원칙 문제가 생기는지, 그리고 테스트용 가짜를 만들 때 어떤 불편이 생기는지 설명하세요.

class LibraryStore(Protocol):
    def find(self, book_id: str) -> Book: ...
    def add(self, loan: Loan) -> None: ...
    def count_by_member(self, member_id: str) -> int: ...
    def delete_all_loans(self) -> None: ...
    def export_csv(self, path: str) -> None: ...
    def backup_to_cloud(self) -> None: ...
모범 답안
ISP 위반: LoanService는 find, add, count_by_member만 쓰는데, 관리자용 delete_all_loans·export_csv·backup_to_cloud까지 아는 인터페이스에 의존하게 됩니다(인터페이스 오염). 백업 방식이 바뀌어 시그니처가 변하면 대출 서비스와 무관한데도 영향을 받습니다.
테스트 불편: 가짜 저장소를 만들 때 쓰지도 않는 메서드 세 개를 빈 구현으로 채워야 합니다.
흔한 함정: "구현 클래스 하나가 다 해 주니 편하다"는 이유로 합치기 쉽습니다. 구현은 하나여도 되지만(InMemoryCatalog와 InMemoryLoans를 한 클래스로 합쳐도 무방), 클라이언트가 보는 인터페이스는 작게 나눠야 합니다.

Q6. [서술형] (학습목표 3)

팀원이 말합니다. "나중에 MySQL이나 MongoDB로 바꿀지도 모르니까, 지금 DatabaseAdapterFactory, 설정 파일로 DB 종류를 고르는 ConfigLoader, 플러그인 등록 시스템까지 다 만들어 두죠." 지금 도서관 시스템(메모리 저장소만 사용, DB 도입 계획 없음) 기준으로 당신의 판단과 이유를 쓰세요.

모범 답안
지금은 만들지 않습니다(YAGNI). 이미 LoanService가 LoanRecorder Protocol에 의존(DIP)하므로, 실제로 DB가 필요해지면 MySqlLoans 클래스 하나를 추가하고 build_library만 바꾸면 됩니다. 팩토리·설정 로더·플러그인은 요구도, 반복된 변경도 없는 추측에 기반한 비용이며, 어떤 DB를 쓸지 모르는 상태에서 만든 추상은 실제 요구와 어긋날 가능성이 큽니다.
왜 "다 만들자"가 매력적인가: SOLID를 배운 직후라 "확장성 = 좋은 설계"로 느껴지기 때문입니다. 좋은 설계는 바꾸기 쉬운 설계이지, 미리 다 바꿔 둔 설계가 아닙니다.
