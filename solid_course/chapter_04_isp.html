04. ISP 인터페이스 분리 원칙

인쇄만 하고 싶은데 왜 팩스 기능까지 알아야 할까? "다 들어 있는" 인터페이스가 구현하는 쪽과 쓰는 쪽을 모두 괴롭히는 이유를 봅니다.

학습목표

  1. ISP를 "클라이언트가 쓰지 않는 메서드에 의존하지 않게 한다"는 관점에서 설명할 수 있다.
  2. 뚱뚱한 인터페이스가 만드는 증상(가짜 구현, 무관한 변경 전파)을 코드에서 찾아낼 수 있다.
  3. typing.Protocol로 역할별 작은 인터페이스를 설계할 수 있다.

개념

인터페이스 분리 원칙(Interface Segregation Principle): 클라이언트는 자신이 사용하지 않는 메서드에 의존하도록 강요받으면 안 된다. 즉, 인터페이스는 그것을 쓰는 클라이언트(역할) 단위로 작게 나눈다.

왜 필요할까요? 인터페이스가 크면 (1) 구현하는 쪽은 할 수 없는 기능까지 억지로 구현해야 하고, (2) 쓰는 쪽은 관심 없는 메서드의 변경에도 함께 흔들립니다. 앞 장에서 본 "NotImplementedError를 던지는 하위 타입"(LSP 위반)은 사실 뚱뚱한 인터페이스가 원인인 경우가 많습니다.

📦 새 개념: 인터페이스 오염 (Interface Pollution)

  • 정의: 일부 구현체·클라이언트에만 필요한 메서드가 공용 인터페이스에 섞여 들어가, 모두가 그 메서드에 엮이는 상태
  • 증상: raise NotImplementedError/pass만 있는 "가짜 구현", 쓰지도 않는 메서드 때문에 생기는 재수정·재배포, 테스트용 가짜 객체를 만들기 번거로움
  • 예: 인쇄만 하는 SimplePrinter가 Machine을 상속하는 바람에 scan_doc, fax_doc까지 구현해야 함

📦 새 개념: 테스트용 가짜 객체 (Fake / Mock)

  • 정의: 테스트에서 진짜 장치·서버 대신 끼워 넣는, 같은 메서드를 가진 간단한 객체. 실제 일은 하지 않고 정해진 값을 돌려주거나 호출 기록만 남긴다
  • 왜 필요?: 프린터·메일 서버 없이도 그것을 쓰는 코드의 동작을 빠르고 안전하게 확인하려고
  • 예: class FakePrinter: def print_doc(self, doc): self.printed.append(doc) — 인터페이스가 작을수록 가짜 객체도 작아진다

상황

사내 문서 출력 시스템. 처음 들여온 기기가 복합기였기 때문에 Machine 인터페이스에 print_doc, scan_doc, fax_doc을 모두 넣었습니다. 인쇄 대기열 PrintQueue도 Machine을 받습니다.

요구가 바뀌는 순간 ①: 각 층에 저렴한 단순 프린터를 들였습니다. Machine을 상속하려니 스캔·팩스 메서드를 "지원 안 함" 예외로 채워야 했고, 어떤 직원의 스캔 보관 스크립트가 이 프린터를 받아 실행 중에 터졌습니다.

요구가 바뀌는 순간 ②: 팩스 업체가 바뀌어 fax_doc에 해상도 인자를 추가해야 합니다. 팩스와 아무 상관 없는 단순 프린터 코드와 인쇄 대기열 테스트까지 고쳐야 합니다.

요구가 바뀌는 순간 ③: 이번엔 스테이플(철하기) 기능이 있는 사무용 프린터가 들어옵니다. Machine에 staple()을 추가하면… 모든 기기에 또 가짜 구현이 생깁니다.

나쁜 코드

아래 코드는 실행은 되지만, Machine 하나에 모든 능력을 몰아넣어 구현체와 클라이언트를 함께 오염시킵니다.

"""
chapter_04_isp.py — ISP(인터페이스 분리 원칙) 예제: 복합기와 프린터

목적
    인쇄·스캔·팩스를 한 덩어리로 묶은 '뚱뚱한' Machine 인터페이스가
    단순 프린터와 그 사용자(클라이언트)를 어떻게 괴롭히는지 보고,
    클라이언트가 실제로 쓰는 기능 단위의 작은 인터페이스(Protocol)로 나눈다.

다루는 원칙
    ISP: 클라이언트는 자신이 사용하지 않는 메서드에 의존하도록 강요받으면 안 된다.
         파이썬에서는 typing.Protocol(구조적 타이핑) 또는 ABC 로 작은 인터페이스를 표현한다.

실행 방법
    python3 chapter_04_isp.py
"""

from abc import ABC, abstractmethod
from typing import Protocol, runtime_checkable


# ======================================================================
# 나쁜 코드: 모든 기능을 담은 뚱뚱한 Machine 인터페이스
# ======================================================================

class Machine(ABC):
    # [문제 1] 인쇄·스캔·팩스를 하나의 인터페이스에 몰아넣었다.
    #   → 이 인터페이스를 '구현하는 쪽'은 할 수 없는 기능까지 구현해야 하고,
    #   → 이 인터페이스를 '사용하는 쪽'은 필요 없는 기능에까지 엮인다(인터페이스 오염).
    @abstractmethod
    def print_doc(self, doc: str) -> str: ...

    @abstractmethod
    def scan_doc(self, doc: str) -> str: ...

    @abstractmethod
    def fax_doc(self, doc: str, number: str) -> str: ...


class BadMultiFunctionPrinter(Machine):
    """복합기: 세 기능을 모두 할 수 있으니 문제없어 보인다."""

    def print_doc(self, doc: str) -> str:
        return f"[복합기] 인쇄: {doc}"

    def scan_doc(self, doc: str) -> str:
        return f"[복합기] 스캔: {doc}.pdf"

    def fax_doc(self, doc: str, number: str) -> str:
        return f"[복합기] 팩스 {number} 로 전송: {doc}"


class BadSimplePrinter(Machine):
    """단순 프린터: 인쇄밖에 못 하는데 Machine 을 상속해야 '프린터'로 인정받는다."""

    def print_doc(self, doc: str) -> str:
        return f"[프린터] 인쇄: {doc}"

    # [문제 2] 못 하는 기능을 억지로 구현 → 예외를 던지는 '가짜 구현'.
    #   → Machine 을 믿고 scan_doc 을 부른 코드는 런타임에 터진다(3장 LSP 위반과 같은 모양).
    def scan_doc(self, doc: str) -> str:
        raise NotImplementedError("이 프린터는 스캔을 지원하지 않습니다")

    # [문제 3] 팩스 시그니처가 바뀌면(예: 해상도 인자 추가) 팩스와 무관한
    #   단순 프린터 코드까지 고쳐야 한다. '쓰지도 않는 메서드'가 변경 이유가 된다.
    def fax_doc(self, doc: str, number: str) -> str:
        raise NotImplementedError("이 프린터는 팩스를 지원하지 않습니다")


class BadPrintQueue:
    # [문제 4] 인쇄만 하는 클라이언트인데 Machine 전체에 의존한다.
    #   → 테스트용 가짜(fake) 객체를 만들 때도 scan/fax 까지 구현해야 하고,
    #   → Machine 에 메서드가 하나 늘 때마다 이 클라이언트의 의존 대상도 같이 커진다.
    def __init__(self, machine: Machine) -> None:
        self.machine = machine

    def run(self, docs: list[str]) -> list[str]:
        return [self.machine.print_doc(d) for d in docs]
번호증상누가 고통받나
[문제 1]세 능력을 한 인터페이스에 묶음모든 구현체와 모든 클라이언트
[문제 2]NotImplementedError 가짜 구현Machine을 믿고 호출한 클라이언트(런타임 오류, LSP 위반으로 이어짐)
[문제 3]팩스 시그니처 변경이 단순 프린터까지 전파팩스와 무관한 구현체
[문제 4]인쇄만 하는 클라이언트가 Machine 전체에 의존클라이언트와 그 테스트 코드

개선 코드

핵심 아이디어: 클라이언트가 실제로 쓰는 역할마다 작은 인터페이스를 만들고, 기기는 할 수 있는 역할만 갖습니다. 파이썬에서는 typing.Protocol로 이를 가볍게 표현할 수 있습니다.

📦 새 개념: Protocol (구조적 타이핑)

  • 정의: "어떤 메서드(시그니처)를 가지고 있으면 이 타입으로 인정한다"를 선언하는 typing 모듈의 기능. 상속 관계가 아니라 구조(모양)로 타입을 판단한다
  • 왜 필요?: 구현 클래스가 인터페이스를 상속하지 않아도 되므로, 작은 인터페이스를 여러 개 만들어도 부담이 없다. 파이썬의 덕 타이핑을 mypy 같은 타입 검사기가 이해하는 형태로 만든다
  • ABC와 차이: ABC는 상속해야 인정(명목적 타이핑)되고 미구현 시 인스턴스 생성을 막는다. Protocol은 상속 없이 모양만 맞으면 인정된다
  • 예: class Printer(Protocol): def print_doc(self, doc: str) -> str: ... → print_doc을 가진 어떤 클래스든 Printer
  • 주의: @runtime_checkable을 붙이면 isinstance로 검사할 수 있지만, 메서드 이름 존재만 확인하고 시그니처는 확인하지 않는다
# ======================================================================
# 개선 코드: 클라이언트가 쓰는 역할 단위로 작은 Protocol 을 나눈다
# ======================================================================

# [해결 1] 역할(능력)별로 인터페이스를 쪼갠다. 각 Protocol 은 메서드 하나뿐이다.
#   Protocol 은 '이런 메서드를 가진 객체면 된다'는 구조적 타이핑이라
#   구현 클래스가 상속하지 않아도 된다(덕 타이핑을 타입 검사기가 이해하는 형태).
#   @runtime_checkable 은 데모에서 isinstance 로 확인해 보려고 붙였다(메서드 존재 여부만 검사).

@runtime_checkable
class Printer(Protocol):
    def print_doc(self, doc: str) -> str: ...


@runtime_checkable
class Scanner(Protocol):
    def scan_doc(self, doc: str) -> str: ...


@runtime_checkable
class Fax(Protocol):
    def fax_doc(self, doc: str, number: str) -> str: ...


class SimplePrinter:
    # [해결 2] 단순 프린터는 할 수 있는 일(print_doc)만 구현한다.
    #   가짜 구현도, NotImplementedError 도 없다. Printer Protocol 을 상속하지 않았지만
    #   print_doc 시그니처가 같으므로 Printer 로 인정된다.
    def print_doc(self, doc: str) -> str:
        return f"[프린터] 인쇄: {doc}"


class MultiFunctionPrinter:
    # [해결 3] 복합기는 여러 역할을 '조합'해서 가진다. 한 클래스가 여러 Protocol 을
    #   동시에 만족하는 것은 자연스럽다. 인터페이스를 나눈다고 구현까지 쪼갤 필요는 없다.
    def print_doc(self, doc: str) -> str:
        return f"[복합기] 인쇄: {doc}"

    def scan_doc(self, doc: str) -> str:
        return f"[복합기] 스캔: {doc}.pdf"

    def fax_doc(self, doc: str, number: str) -> str:
        return f"[복합기] 팩스 {number} 로 전송: {doc}"


class PrintQueue:
    # [해결 4] 인쇄 클라이언트는 Printer 만 안다. 팩스 시그니처가 바뀌어도 영향이 없고,
    #   테스트할 때는 print_doc 하나짜리 가짜 객체면 충분하다.
    def __init__(self, printer: Printer) -> None:
        self.printer = printer

    def run(self, docs: list[str]) -> list[str]:
        return [self.printer.print_doc(d) for d in docs]


class ScanArchive:
    # [해결 5] 스캔 보관 클라이언트는 Scanner 만 요구한다.
    #   SimplePrinter 를 넘기면 '실행 중 예외'가 아니라 '타입 검사 단계의 오류'로 잡힌다.
    def __init__(self, scanner: Scanner) -> None:
        self.scanner = scanner

    def archive(self, doc: str) -> str:
        return f"보관 완료 <- {self.scanner.scan_doc(doc)}"


# ----------------------------------------------------------------------
# 요구 변경: "스테이플(철하기) 기능이 있는 사무용 프린터를 들여왔어요"
#   - 나쁜 코드: Machine 에 staple() 을 추가 → 복합기·단순 프린터 '모두'에
#     staple 구현(대부분 NotImplementedError)을 추가해야 한다.
#   - 개선 코드: Stapler Protocol 과 새 기기 클래스만 추가. 기존 클래스·클라이언트는 그대로.
# ----------------------------------------------------------------------

@runtime_checkable
class Stapler(Protocol):
    def staple(self, pages: int) -> str: ...


class OfficePrinter:
    """인쇄 + 스테이플만 하는 사무용 프린터."""

    def print_doc(self, doc: str) -> str:
        return f"[사무용] 인쇄: {doc}"

    def staple(self, pages: int) -> str:
        return f"[사무용] {pages}장 철하기 완료"


class BookletService:
    # 인쇄와 철하기가 '둘 다' 필요한 클라이언트는 두 역할을 각각 받는다.
    #   (같은 객체를 두 번 넘겨도 되고, 서로 다른 기계를 조합해도 된다.)
    def __init__(self, printer: Printer, stapler: Stapler) -> None:
        self.printer = printer
        self.stapler = stapler

    def make(self, pages: list[str]) -> list[str]:
        out = [self.printer.print_doc(p) for p in pages]
        out.append(self.stapler.staple(len(pages)))
        return out


if __name__ == "__main__":
    print("=== 나쁜 코드: 뚱뚱한 Machine 인터페이스 ===")
    machines: list[Machine] = [BadMultiFunctionPrinter(), BadSimplePrinter()]
    for m in machines:
        print(" ", BadPrintQueue(m).run(["보고서"])[0])
        # Machine 타입이니 scan_doc 이 있다고 믿고 불렀다가…
        try:
            print(" ", m.scan_doc("계약서"))
        except NotImplementedError as e:
            print("  [예외]", e)

    print()
    print("=== 개선 코드: 역할별 작은 Protocol ===")
    simple, mfp, office = SimplePrinter(), MultiFunctionPrinter(), OfficePrinter()
    for p in (simple, mfp, office):
        print(" ", PrintQueue(p).run(["보고서"])[0])
    print(" ", ScanArchive(mfp).archive("계약서"))
    for line in BookletService(office, office).make(["1쪽", "2쪽", "3쪽"]):
        print(" ", line)

    print()
    print("=== 누가 어떤 역할을 만족하나? (구조적 타이핑) ===")
    for obj in (simple, mfp, office):
        roles = [proto.__name__ for proto in (Printer, Scanner, Fax, Stapler) if isinstance(obj, proto)]
        print(f"  {type(obj).__name__:22} -> {', '.join(roles)}")

같은 요구 변경을 이제 어떻게 흡수하나

  • 단순 프린터 추가: print_doc만 구현. 가짜 구현 없음. 스캔 보관에 잘못 넘기면 타입 검사기가 실행 전에 경고합니다.
  • 팩스 시그니처 변경: Fax Protocol과 이를 구현한 복합기, 그리고 팩스를 쓰는 클라이언트만 바뀝니다. SimplePrinter, PrintQueue는 영향 없음.
  • 스테이플 기능 추가: Stapler Protocol과 OfficePrinter만 추가. 기존 클래스·클라이언트 수정 0줄.

  OfficePrinter          -> Printer, Stapler

💡 핵심 포인트

인터페이스를 나누는 기준은 "기기가 무엇을 할 수 있나"보다 "클라이언트가 무엇을 필요로 하나"입니다. PrintQueue는 인쇄만, ScanArchive는 스캔만, BookletService는 인쇄+철하기를 요구합니다. 그리고 인터페이스를 쪼갠다고 구현까지 쪼갤 필요는 없습니다—MultiFunctionPrinter 하나가 세 역할을 모두 만족합니다.

정리

나쁜 코드 (뚱뚱한 Machine)개선 코드 (역할별 Protocol)
인터페이스 크기메서드 3개(+계속 증가)역할당 메서드 1개
단순 프린터가짜 구현 2개print_doc만
클라이언트 의존모두 Machine 전체필요한 역할만 (Printer, Scanner…)
팩스 변경 영향모든 구현체팩스 관련 코드만
새 능력 추가모든 구현체 수정Protocol 1개 + 해당 기기만
잘못된 사용 발견실행 중 예외정적 타입 검사

⚠️ 흔한 오해

  • "메서드 하나당 인터페이스 하나"가 규칙: 아닙니다. 기준은 클라이언트가 함께 쓰는 메서드 묶음입니다. open/read/close처럼 항상 같이 쓰이는 메서드는 한 인터페이스에 두는 게 맞습니다.
  • "ISP는 정적 타입 언어 얘기라 파이썬과 무관": 파이썬에서도 큰 ABC를 상속하면 가짜 구현이 생기고, 타입 힌트가 클라이언트의 의존을 드러냅니다. Protocol로 그 의존을 작게 만들 수 있습니다.
  • "ISP는 구현 클래스를 작게 쪼개라는 뜻": 쪼개는 것은 인터페이스입니다. 복합기 클래스는 하나로 둬도 됩니다.

💡 과잉 적용 주의

구현체가 하나뿐이고 클라이언트도 하나뿐인데 Protocol을 잔뜩 만드는 것은 읽을 파일만 늘립니다. "이 메서드를 쓰지 않는 클라이언트/구현체가 실제로 생겼다"(가짜 구현이 처음 등장했다)는 신호가 왔을 때 분리해도 늦지 않습니다.

이해 점검

Q1. [개념 확인] (학습목표 1)

ISP에서 인터페이스를 나누는 가장 적절한 기준은?

  1. 메서드 하나마다 인터페이스를 하나씩 만든다.
  2. 구현 클래스의 코드 줄 수가 일정 이상이면 나눈다.
  3. 상속 깊이가 3단계를 넘지 않도록 나눈다.
  4. 그 인터페이스를 사용하는 클라이언트가 실제로 필요로 하는 메서드 묶음별로 나눈다.
정답: 4
ISP의 주어는 클라이언트입니다. "클라이언트가 쓰지 않는 메서드에 의존하지 않게" 하려면 클라이언트가 함께 쓰는 메서드 묶음이 기준이 됩니다.
왜 오답이 매력적인가: 1은 "작을수록 좋다"는 단순화라 끌리지만, 항상 함께 쓰는 메서드까지 쪼개면 클라이언트가 여러 타입을 받아야 해 오히려 불편합니다. 2는 클래스 크기(SRP 쪽 관심사)와 인터페이스 크기를 혼동한 것입니다. 3은 ISP와 무관한 기준입니다.

Q2. [개념 확인] (학습목표 3)

다음 코드에서 Label 클래스는 Printer를 상속하지 않았지만, 정적 타입 검사기는 PrintQueue(Label())을 올바른 사용으로 인정한다.

class Printer(Protocol):
    def print_doc(self, doc: str) -> str: ...

class Label:
    def print_doc(self, doc: str) -> str:
        return f"라벨: {doc}"
  1. O
  2. X
정답: O
Protocol은 구조적 타이핑입니다. 같은 이름·시그니처의 print_doc을 가지면 상속 없이도 Printer로 인정됩니다. 본문의 SimplePrinter도 같은 방식입니다.
왜 X가 매력적인가: ABC(명목적 타이핑)에 익숙하면 "상속해야 그 타입"이라고 생각하기 쉽습니다. ABC였다면 상속(또는 register)이 필요합니다.

Q3. [위반 찾기] (학습목표 2)

도서관 키오스크용 인터페이스입니다. 대출 화면(LoanScreen)은 scan_card와 show만 쓰고, 관리자 도구는 reboot와 update_firmware만 씁니다. 이 설계에서 ISP 위반의 가장 직접적인 증거는?

class Kiosk(ABC):
    @abstractmethod
    def scan_card(self) -> str: ...
    @abstractmethod
    def show(self, msg: str) -> None: ...
    @abstractmethod
    def reboot(self) -> None: ...
    @abstractmethod
    def update_firmware(self, version: str) -> None: ...

class MockKiosk(Kiosk):          # LoanScreen 테스트용 가짜
    def scan_card(self) -> str: return "CARD-001"
    def show(self, msg: str) -> None: print(msg)
    def reboot(self) -> None: pass
    def update_firmware(self, version: str) -> None: pass

class LoanScreen:
    def __init__(self, kiosk: Kiosk) -> None:
        self.kiosk = kiosk
  1. Kiosk가 추상 클래스(ABC)로 정의되어 있다.
  2. scan_card가 문자열을 반환한다.
  3. LoanScreen 테스트용 가짜 객체가 쓰지도 않는 reboot, update_firmware를 빈 구현으로 채워야 한다.
  4. LoanScreen이 생성자에서 키오스크를 받는다.
정답: 3
쓰지 않는 메서드를 pass로 채우는 가짜 구현이 인터페이스 오염의 대표 증상입니다. LoanScreen은 scan_card/show만 쓰는데 Kiosk 전체에 의존하므로, 관리 기능 시그니처가 바뀌면 대출 화면 테스트까지 고쳐야 합니다. 개선: 대출 화면이 함께 쓰는 scan_card/show 묶음과 관리자 도구가 쓰는 reboot/update_firmware 묶음으로, 클라이언트별 Protocol을 나눕니다(Q4).
왜 오답이 매력적인가: 1은 "ABC가 문제"로 보이기 쉽지만, 작은 ABC는 ISP를 지킬 수 있습니다—문제는 크기입니다. 4는 오히려 바람직한 의존성 주입(다음 장 DIP)입니다. 2는 무관합니다.

Q4. [리팩터링 실습] (학습목표 3)

Q3의 Kiosk를 ISP에 맞게 Protocol로 나누고, LoanScreen과 MockKiosk가 어떻게 바뀌는지 작성해 보세요.

모범 답안 예시 
class LoanTerminal(Protocol):      # 대출 화면이 '함께' 쓰는 묶음
    def scan_card(self) -> str: ...
    def show(self, msg: str) -> None: ...

class Maintenance(Protocol):       # 관리자 도구가 '함께' 쓰는 묶음
    def reboot(self) -> None: ...
    def update_firmware(self, version: str) -> None: ...

class LoanScreen:
    def __init__(self, terminal: LoanTerminal) -> None:
        self.terminal = terminal

class FakeLoanTerminal:            # 상속 불필요, 필요한 두 메서드만
    def scan_card(self) -> str: return "CARD-001"
    def show(self, msg: str) -> None: print(msg)

screen = LoanScreen(FakeLoanTerminal())
# 실제 키오스크 클래스는 네 메서드를 모두 구현해 두 Protocol을 동시에 만족한다
채점 포인트: (1) 클라이언트가 함께 쓰는 메서드 묶음대로 나눴는가—대출 화면은 scan_card와 show를 항상 함께 쓰므로 한 Protocol(LoanTerminal)로, 관리자 도구는 reboot와 update_firmware를 함께 쓰므로 Maintenance로 묶는다. 메서드마다 Protocol을 하나씩 만드는 것은 과잉 분리다(카드 리더와 화면이 서로 다른 장치로 따로 바뀌는 요구가 실제로 생겼다면 그때 나눈다). (2) LoanScreen의 타입 힌트가 작은 역할로 바뀌었는가. (3) 가짜 객체에서 빈 구현이 사라졌는가. 실제 키오스크 클래스는 네 메서드를 모두 가진 채 하나로 남아도 된다.

Q5. [서술형] (학습목표 1, 2)

(1) 뚱뚱한 인터페이스가 3장의 LSP 위반으로 이어지는 과정을 본문의 BadSimplePrinter를 예로 설명하세요. (2) 메서드가 2개뿐인 Reader(Protocol)(read, close)를 또 쪼개야 하는지 판단하고 이유를 쓰세요.

채점 포인트
  • (1) Machine이 "스캔할 수 있다"를 약속하므로 단순 프린터는 할 수 없는 scan_doc을 NotImplementedError로 채운다 → Machine 자리에 넣으면 계약(호출 가능)을 깨므로 치환 불가 = LSP 위반. 즉 ISP 위반(큰 인터페이스)이 원인, LSP 위반(가짜 구현)이 결과로 나타난다.
  • (2) 대체로 쪼갤 필요 없다. read와 close는 같은 클라이언트가 함께 쓰는 묶음이고, 구현체가 둘 중 하나만 지원할 이유도 없다. "쓰지 않는 메서드를 강요받는 클라이언트/구현체"가 실제로 생겼을 때 나누는 것이 맞으며, 메서드 수 자체는 기준이 아니다(과잉 적용 경계).
왜 헷갈리는가: "인터페이스는 작을수록 좋다"를 규칙으로 외우면 (2)에서 무조건 쪼개는 답을 쓰기 쉽습니다.
