00. OOP 복습: SOLID를 배우기 전에

SOLID 5원칙은 모두 "클래스를 어떻게 나누고 연결할까"에 대한 이야기입니다. 그 전에 꼭 필요한 도구 다섯 가지를 도형 예제로 다시 다져 봅니다.

학습목표

  1. 추상화·상속·다형성을 각각 한 문장으로 설명하고, 도형 예제 코드에서 해당 부분을 찾을 수 있다.
  2. abc.ABC와 @abstractmethod로 추상 클래스를 작성하고, 구현을 빠뜨렸을 때 무슨 일이 생기는지 예측할 수 있다.
  3. 결합도와 응집도를 기준으로 두 설계 중 더 나은 쪽을 판단할 수 있다.

개념

한 문장 요약: 객체지향은 "데이터와 그 데이터를 다루는 행동을 한 객체에 모으고, 객체끼리는 약속(인터페이스)으로만 대화하게 하는" 설계 방식입니다.

📦 새 개념: 인터페이스 (Interface)

  • 정의: 객체가 바깥에 약속하는 메서드 목록(이름·인자·반환값). 내부 구현은 포함하지 않는다
  • 왜 필요?: 쓰는 쪽이 구현이 아닌 약속에만 기대게 해서, 구현을 바꿔도 쓰는 쪽은 그대로 두려고
  • 예: "도형이라면 area()와 perimeter()를 가진다" — 파이썬에서는 ABC(아래)나 Protocol(4장)로 표현

왜 필요할까요? 프로그램은 반드시 바뀝니다. 바뀌는 순간 고칠 곳이 한 곳이면 쉽고, 여기저기면 버그가 납니다. 아래 도구들은 모두 "고칠 곳을 한 곳으로 모으기" 위한 것입니다.

추상화

원·사각형·삼각형은 모두 다르지만 "넓이와 둘레를 구할 수 있다"는 공통점이 있습니다. 이렇게 세부를 감추고 공통의 핵심만 남기는 것이 추상화입니다.

📦 새 개념: 추상화 (Abstraction)

  • 정의: 여러 대상에서 공통으로 중요한 성질만 뽑아내고, 세부 구현은 감추는 것
  • 왜 필요?: 사용하는 쪽이 "어떻게"를 몰라도 "무엇을"만 알면 쓸 수 있게 하려고
  • 예: "도형은 area()를 가진다" — 원의 공식(πr²)은 몰라도 된다

상속

📦 새 개념: 상속 (Inheritance)

  • 정의: 부모 클래스의 속성·메서드를 자식 클래스가 물려받고, 필요한 부분을 다시 정의(오버라이드)하는 것
  • 왜 필요?: 공통 코드를 한 번만 쓰고, "A는 B의 한 종류(is-a)"라는 관계를 코드로 표현하려고
  • 예: class Circle(Shape): — 원은 도형의 한 종류, describe()를 그대로 물려받음

다형성

📦 새 개념: 다형성 (Polymorphism)

  • 정의: 같은 메서드 호출이 실제 객체의 종류에 따라 서로 다르게 동작하는 성질
  • 왜 필요?: 호출하는 쪽에서 "너 원이야? 사각형이야?" 묻는 if-elif를 없애려고
  • 예: for s in shapes: s.area() — 원은 πr², 사각형은 가로×세로로 계산

📦 새 개념: 덕 타이핑 (Duck Typing)

  • 정의: 상속 관계를 따지지 않고 "필요한 메서드를 가지고 있으면 그 타입으로 쓴다"는 파이썬의 방식("오리처럼 걸으면 오리다")
  • 왜 필요?: 공통 부모 클래스 없이도 다형성을 쓸 수 있어, 상속을 강요하지 않으려고
  • 예: Shape를 상속하지 않은 클래스라도 area()만 있으면 for s in shapes: s.area()가 동작한다

추상 클래스(ABC)

📦 새 개념: 추상 클래스 (ABC)

  • 정의: 직접 인스턴스를 만들 수 없고, 하위 클래스가 구현해야 할 메서드를 강제하는 클래스
  • 왜 필요?: "도형이라면 반드시 area가 있어야 한다"는 약속을 말이 아닌 코드로 못 박기 위해
  • 예: class Shape(ABC): + @abstractmethod def area(self) — 구현을 빠뜨린 자식은 생성 시 TypeError

결합도와 응집도

📦 새 개념: 결합도(Coupling) / 응집도(Cohesion)

  • 정의: 결합도 = 모듈끼리 서로 얼마나 깊이 알고 의존하는가 / 응집도 = 한 모듈 안의 요소들이 얼마나 같은 목적으로 모여 있는가
  • 왜 필요?: 좋은 설계의 물리량. 결합도는 낮게, 응집도는 높게가 목표다. SOLID 5원칙은 모두 이 목표를 위한 구체적인 규칙이다
  • 예: 원의 데이터와 공식이 Circle에 모여 있으면 응집도↑, total_area가 Shape 약속만 알면 결합도↓

상황

수학 학습 앱을 만드는 중입니다. 처음엔 원과 사각형만 있으면 된다고 해서, 도형을 딕셔너리로 두고 area(), perimeter() 함수 안에서 kind 문자열로 분기했습니다.

그런데 다음 주 기획 회의에서 "삼각형도 추가해 주세요. 나중에 오각형, 부채꼴도요."라는 요구가 나왔습니다. 도형 하나를 늘릴 때마다 어디를 몇 군데 고쳐야 할까요?

나쁜 코드

파일 상단(설명과 import)입니다.

"""00장. OOP 복습: SOLID를 배우기 전에 — 도형 클래스 계층

목적
    SOLID 5원칙을 이해하는 데 꼭 필요한 객체지향 기초 도구
    (추상화, 상속, 다형성, 추상 클래스(ABC), 결합도/응집도)를
    '도형 넓이 계산'이라는 작은 예제로 복습한다.

다루는 원칙
    아직 특정 SOLID 원칙은 아니다. 다만 나쁜 코드에서 보이는 문제들
    (if-elif 분기 폭증, 데이터와 행동의 분리)이 이후 SRP·OCP·LSP의 출발점이 된다.

실행 방법
    python3 chapter_00_oop_review.py
"""
from __future__ import annotations

import math
from abc import ABC, abstractmethod

아래 코드는 실행은 잘 됩니다. 하지만 주석의 [문제 1~4]를 확인해 보세요.

# ===== 나쁜 코드: 도형 '종류' 문자열로 분기하는 절차적 설계 =====

# [문제 1] 도형이 그냥 딕셔너리(데이터 덩어리)다.
#          "원은 반지름이 필요하다" 같은 규칙을 아무도 지켜 주지 않는다.
#          오타("radius" → "radious")가 나도 실행해 보기 전엔 모른다.
def make_shape(kind: str, **data: float) -> dict:
    return {"kind": kind, **data}


# [문제 2] 넓이 계산 지식이 도형 바깥 함수에 모여 있다(낮은 응집도).
#          원의 정보는 make_shape에, 원의 계산은 여기에 흩어져 있다.
def area(shape: dict) -> float:
    # [문제 3] 도형 종류마다 if-elif가 늘어난다.
    #          '삼각형'을 추가하려면 이 함수를 열어 고쳐야 한다.
    if shape["kind"] == "circle":
        return math.pi * shape["radius"] ** 2
    elif shape["kind"] == "rect":
        return shape["width"] * shape["height"]
    else:
        raise ValueError(f"모르는 도형: {shape['kind']}")


# [문제 4] 둘레 계산에도 '똑같은 분기'가 또 등장한다(높은 결합도).
#          area, perimeter, draw ... 기능이 늘수록 도형 종류 문자열에
#          의존하는 곳이 늘어나, 새 도형 하나에 여러 함수를 함께 고쳐야 한다.
def perimeter(shape: dict) -> float:
    if shape["kind"] == "circle":
        return 2 * math.pi * shape["radius"]
    elif shape["kind"] == "rect":
        return 2 * (shape["width"] + shape["height"])
    else:
        raise ValueError(f"모르는 도형: {shape['kind']}")
  • [문제 1] 도형이 규칙 없는 딕셔너리라 필수 값(반지름 등)을 강제할 수 없습니다.
  • [문제 2] 원에 관한 지식이 여러 함수에 흩어져 있습니다 → 응집도가 낮음.
  • [문제 3·4] 같은 if-elif가 기능마다 반복됩니다. 삼각형 하나를 추가하려면 area와 perimeter 둘 다 고쳐야 합니다 → 결합도가 높음.

개선 코드

# ===== 개선 코드: 추상 클래스 + 상속 + 다형성 =====

# [해결 1] 추상화: "도형이라면 넓이와 둘레를 계산할 수 있다"는 공통 약속만
#          뽑아낸다. 어떻게 계산하는지는 감춘다.
# [해결 2] 추상 클래스(ABC): @abstractmethod로 그 약속을 코드로 못 박는다.
#          Shape()를 직접 만들 수 없고, 하위 클래스가 area/perimeter를
#          빠뜨리면 인스턴스화(Square(...) 호출) 때 __init__이 실행되기
#          전에 TypeError가 난다.
class Shape(ABC):
    @abstractmethod
    def area(self) -> float:
        """도형의 넓이를 돌려준다."""

    @abstractmethod
    def perimeter(self) -> float:
        """도형의 둘레를 돌려준다."""

    # 공통 행동은 부모에 한 번만 둔다. 하위 클래스는 자동으로 물려받는다.
    def describe(self) -> str:
        return f"{type(self).__name__}: 넓이={self.area():.2f}, 둘레={self.perimeter():.2f}"


# [해결 3] 상속 + 높은 응집도: 원에 관한 데이터(radius)와 계산(area, perimeter)이
#          Circle 한 곳에 모인다. 원의 공식이 바뀌면 이 클래스만 고친다.
class Circle(Shape):
    def __init__(self, radius: float) -> None:
        self.radius = radius

    def area(self) -> float:
        return math.pi * self.radius ** 2

    def perimeter(self) -> float:
        return 2 * math.pi * self.radius


class Rectangle(Shape):
    def __init__(self, width: float, height: float) -> None:
        self.width = width
        self.height = height

    def area(self) -> float:
        return self.width * self.height

    def perimeter(self) -> float:
        return 2 * (self.width + self.height)


# [해결 4] 새 도형 추가 = 새 클래스 하나 추가. 기존 코드는 한 줄도 안 고친다.
#          (나쁜 코드에선 area, perimeter 두 함수를 모두 열어야 했다.)
class Triangle(Shape):
    def __init__(self, a: float, b: float, c: float) -> None:
        self.a, self.b, self.c = a, b, c

    def area(self) -> float:
        s = self.perimeter() / 2  # 헤론의 공식
        return math.sqrt(s * (s - self.a) * (s - self.b) * (s - self.c))

    def perimeter(self) -> float:
        return self.a + self.b + self.c


# [해결 5] 다형성 + 낮은 결합도: 이 함수는 Shape라는 '약속'에만 의존한다.
#          실제 객체가 원이든 삼각형이든 shape.area()를 부르면
#          각자 자기 방식으로 계산한다. 그래서 if-elif가 사라진다.
def total_area(shapes: list[Shape]) -> float:
    return sum(shape.area() for shape in shapes)
  • [해결 1·2] Shape가 "넓이·둘레를 구할 수 있다"는 약속(추상화)을 ABC로 강제합니다.
  • [해결 3] 각 도형 클래스가 자기 데이터와 계산을 함께 가집니다(응집도↑).
  • [해결 4] 삼각형 추가 요구는 Triangle 클래스를 새로 쓰는 것만으로 해결됐습니다. 기존 코드는 수정하지 않았습니다.
  • [해결 5] total_area는 구체적인 도형 종류를 모릅니다(결합도↓). 다형성 덕분입니다.

실행 데모:

# ===== 실행 데모 =====
if __name__ == "__main__":
    print("--- 나쁜 코드 ---")
    old_shapes = [make_shape("circle", radius=1), make_shape("rect", width=2, height=3)]
    for s in old_shapes:
        print(s["kind"], f"넓이={area(s):.2f}", f"둘레={perimeter(s):.2f}")
    try:
        area(make_shape("triangle", a=3, b=4, c=5))
    except ValueError as e:
        # 새 도형을 지원하려면 area/perimeter를 모두 고쳐야 한다는 신호
        print("삼각형 추가 실패 →", e)

    print("--- 개선 코드 ---")
    shapes: list[Shape] = [Circle(1), Rectangle(2, 3), Triangle(3, 4, 5)]
    for s in shapes:
        print(s.describe())  # 같은 호출, 다른 동작 = 다형성
    print(f"전체 넓이 합계: {total_area(shapes):.2f}")

    try:
        Shape()  # type: ignore[abstract]
    except TypeError as e:
        # 추상 클래스는 직접 만들 수 없다: '약속'일 뿐 실체가 아니기 때문
        print("Shape() 생성 실패 →", type(e).__name__)

💡 핵심 포인트

"새 기능 = 새 클래스 추가, 기존 코드는 그대로" — 이 감각이 02장 OCP의 핵심이 됩니다. 그리고 "한 클래스엔 한 가지 이유로 바뀌는 것만" 모으는 감각이 01장 SRP입니다.

정리

관점나쁜 코드 (딕셔너리 + if-elif)개선 코드 (ABC + 다형성)
새 도형 추가area, perimeter 등 모든 분기 함수 수정새 클래스 하나 추가
필수 메서드 강제불가능(실행해 봐야 앎)@abstractmethod가 생성 시점에 막음
응집도낮음(원의 지식이 흩어짐)높음(원의 모든 것이 Circle에)
결합도높음(모든 함수가 kind 문자열에 의존)낮음(Shape 약속에만 의존)

⚠️ 흔한 오해

  • "상속은 코드 재사용 도구다" — 재사용만을 위한 상속은 위험합니다. 자식이 부모의 약속을 지킬 수 있을 때(is-a)만 상속하세요. 이 문제는 03장 LSP에서 깊게 다룹니다.
  • "if-elif는 무조건 나쁘다" — 종류가 고정되어 거의 늘지 않는다면 단순한 분기가 더 읽기 쉽습니다. 종류가 계속 늘어나는 곳이 다형성을 쓸 자리입니다.
  • 과잉 적용 주의: 도형이 하나뿐인 프로그램에 ABC부터 만드는 것은 불필요한 복잡도입니다.

이해 점검

Q1. [개념 확인] (학습목표 1)

for s in shapes: print(s.area())에서 원은 πr², 사각형은 가로×세로로 계산됩니다. 이 성질을 무엇이라 하나요?

  1. 캡슐화
  2. 상속
  3. 다형성
  4. 추상 클래스
정답: 3번 다형성
같은 호출(s.area())이 실제 객체의 종류에 따라 다르게 동작하는 것이 다형성입니다.
왜 2번이 매력적인가? 다형성은 상속 구조 위에서 자주 나타나서 헷갈리지만, 상속은 "물려받는 관계"이고 다형성은 "같은 호출, 다른 동작"이라는 결과입니다. 파이썬에선 상속 없이도(덕 타이핑) 다형성이 가능합니다.

Q2. [개념 확인] (학습목표 2)

Shape(ABC)에 @abstractmethod perimeter가 있는데, class Square(Shape)가 area만 구현했습니다. Square(2)는 정상적으로 만들어지고, perimeter()를 호출할 때 비로소 에러가 난다. (O/X)

  1. O
  2. X
정답: X
추상 메서드를 하나라도 구현하지 않은 클래스는 클래스를 호출해 인스턴스를 생성할 때(Square(2)) __init__이 실행되기도 전에 TypeError: Can't instantiate abstract class ...가 발생하고 인스턴스가 만들어지지 않습니다. perimeter()를 호출할 때까지 기다리지 않고 인스턴스화 단계에서 막는 것이 ABC의 장점입니다.
왜 O가 매력적인가? 일반 클래스에서 없는 메서드를 부르면 호출 시점에 AttributeError가 나기 때문에, ABC도 그럴 것이라 착각하기 쉽습니다.

Q3. [위반 찾기] (학습목표 3)

다음 코드에 "부채꼴(Sector)" 도형을 추가하려 합니다. 이 설계의 가장 큰 문제는?

def area(shape: dict) -> float:
    if shape["kind"] == "circle": ...
    elif shape["kind"] == "rect": ...

def perimeter(shape: dict) -> float:
    if shape["kind"] == "circle": ...
    elif shape["kind"] == "rect": ...

def draw(shape: dict) -> None:
    if shape["kind"] == "circle": ...
    elif shape["kind"] == "rect": ...
  1. 함수 이름이 너무 짧다
  2. 도형 종류 문자열에 여러 함수가 의존해, 새 도형마다 세 함수를 모두 고쳐야 한다(결합도↑, 응집도↓)
  3. 딕셔너리는 파이썬에서 느리다
  4. 타입 힌트가 dict라서 실행이 안 된다
정답: 2번
부채꼴의 지식이 세 함수에 흩어져 들어가야 하고, 하나라도 빠뜨리면 실행 중 오류가 납니다.
왜 4번이 매력적인가? 타입 힌트가 허술해 보이지만, 파이썬에서 타입 힌트는 실행에 영향을 주지 않습니다. 문제는 성능·문법이 아니라 변경에 취약한 구조입니다.

Q4. [리팩터링 실습] (학습목표 2, 3)

본문의 개선 코드에 정사각형 Square(side)를 추가하세요. 어떤 기존 코드를 고쳐야 하나요? 직접 작성한 뒤 total_area([Square(2), Circle(1)])의 결과를 확인해 보세요.

예시 답안 
class Square(Shape):
    def __init__(self, side: float) -> None:
        self.side = side

    def area(self) -> float:
        return self.side ** 2

    def perimeter(self) -> float:
        return 4 * self.side
기존 코드는 한 줄도 고치지 않습니다. 결과는 4 + π ≈ 7.14입니다.
흔한 실수: Square(Rectangle)로 상속하고 싶어지는데, 가로·세로를 따로 바꿀 수 있는 사각형의 약속을 정사각형이 지킬 수 있을지는 03장 LSP에서 다시 따져 봅니다. 지금은 Shape를 직접 상속하는 쪽이 안전합니다.

Q5. [서술형] (학습목표 3)

"도형이 원 하나뿐이고 앞으로도 늘 계획이 없는 계산기"에도 Shape(ABC) 계층을 만들어야 할까요? 결합도·응집도와 비용 관점에서 2~3문장으로 답하세요.

모범 답안 요지: 꼭 그럴 필요는 없습니다. 추상화는 "종류가 늘어나 변경이 여러 곳에 퍼질 때" 결합도를 낮추려고 쓰는 도구인데, 종류가 하나뿐이면 얻는 이득이 없고 클래스·파일만 늘어 읽기 어려워집니다. 도형이 실제로 두 번째, 세 번째로 늘어나는 시점에 추상화를 도입해도 늦지 않습니다.
채점 포인트: ① 추상화의 목적(변경 흡수) 언급 ② 비용(복잡도) 언급 ③ 도입 시점 판단.
