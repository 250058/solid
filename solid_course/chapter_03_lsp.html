03. LSP 리스코프 치환 원칙

"펭귄은 새다"는 맞는 말인데, 왜 코드에서는 펭귄이 Bird를 상속하면 안 될까? 답은 분류가 아니라 계약에 있습니다.

학습목표

  1. LSP를 계약(사전조건·사후조건·불변식)의 언어로 설명할 수 있다.
  2. 하위 클래스가 사전조건을 강화하거나 사후조건을 약화하는 코드를 보고 LSP 위반을 찾아낼 수 있다.
  3. 계약을 지킬 수 있는 타입끼리 묶도록 상속 계층을 재설계할 수 있다.

개념

리스코프 치환 원칙(Liskov Substitution Principle): 상위 타입 T를 사용하는 코드는, 그 자리에 어떤 하위 타입 S를 넣어도 T가 약속한 그대로 올바르게 동작해야 한다.

왜 필요할까요? 다형성의 가치는 "구체 타입을 몰라도 상위 타입만 믿고 호출할 수 있다"는 데 있습니다. 하위 타입 하나가 그 믿음을 깨면, 클라이언트는 다시 isinstance로 타입을 하나하나 검사해야 하고 다형성의 이점이 사라집니다. 앞 장의 OCP(확장에 열림)도 하위 타입이 안전하게 끼워질 수 있을 때만 성립합니다.

📦 새 개념: 계약에 의한 설계 (Design by Contract)

  • 정의: 메서드를 "호출자와 구현자 사이의 계약"으로 보고, 세 가지 약속을 명시하는 설계 방식
    • 사전조건: 호출자가 지켜야 할 입력 조건 (예: altitude > 0)
    • 사후조건: 구현자가 호출 후 보장하는 결과 (예: self.altitude == altitude)
    • 불변식: 객체가 언제나 유지하는 상태 (예: self.altitude >= 0)
  • 왜 필요?: "이 메서드를 믿어도 되는 범위"를 분명히 해야, 하위 타입이 그 범위를 지키는지 판단할 수 있기 때문
  • 예: 파이썬에서는 docstring에 계약을 적고, 입력 검사(raise ValueError)와 assert로 코드에 드러낸다

💡 다시 보기: assert

1장에서 배운 assert로 사후조건·불변식을 코드로 확인합니다. 사전조건(입력 검사)에는 raise ValueError를 씁니다.

📦 새 개념: 치환 가능성 (Substitutability)

  • 정의: 하위 타입 객체를 상위 타입 자리에 넣어도 클라이언트가 차이를 눈치채지 못하고 정상 동작하는 성질
  • 판정 규칙: 하위 타입은
    • 사전조건을 강화하면 안 된다 (같거나 더 너그럽게 받아야 함)
    • 사후조건을 약화하면 안 된다 (같거나 더 많이 보장해야 함)
    • 상위 타입의 불변식을 유지해야 한다
  • 예: Eagle.fly()가 고도 도달 + 활공 로그까지 남기면 OK(사후조건 강화), Ostrich.fly()가 아무것도 안 하면 위반(사후조건 약화)

💡 핵심 포인트

LSP의 질문은 "S는 T의 일종인가(is-a)?"가 아니라 "S는 T의 계약을 지킬 수 있는가?"입니다. 현실의 분류와 코드의 타입 계층은 다를 수 있습니다.

상황

조류 생태 시뮬레이터를 만들고 있습니다. 처음에는 참새만 있었기에 Bird에 fly(altitude)를 넣고 "고도가 0보다 크면 그 고도까지 올라간다"고 문서에 적었습니다. 철새 이동 함수 migrate()는 Bird 목록을 받아 모두 fly(100)을 부릅니다.

요구가 바뀌는 순간: "남극관에 펭귄을, 초원관에 타조를, 정원관에 벌새를 추가해 주세요." 펭귄도 타조도 벌새도 분명 새이니 Bird를 상속했습니다. 그러자…

  • 펭귄은 fly()에서 예외를 던져 시뮬레이션이 멈췄고,
  • 타조는 조용히 아무 일도 안 해서 고도 통계가 몇 주째 틀려 있었고,
  • 벌새는 "10m 이하만 가능"이라며 100m 요청을 거절했습니다.

급한 김에 migrate()에 if isinstance(bird, Penguin): continue를 넣었는데, 다음 주에는 키위가 들어온다고 합니다.

나쁜 코드

아래 코드는 실행은 되지만 하위 타입들이 BadBird의 계약을 각기 다른 방식으로 깨뜨립니다. 주석의 번호와 함께 읽으세요.

"""
chapter_03_lsp.py — LSP(리스코프 치환 원칙) 예제: 새(Bird)와 펭귄

목적
    "펭귄은 새다(is-a)"라는 현실의 분류를 그대로 상속으로 옮기면
    부모 타입의 '계약(사전조건·사후조건·불변식)'이 깨지는 과정을 보고,
    계약을 지킬 수 있는 타입 계층으로 다시 설계한다.

다루는 원칙
    LSP: 상위 타입 T를 쓰는 코드는, T 자리에 어떤 하위 타입 S를 넣어도
         '계약이 약속한 그대로' 올바르게 동작해야 한다.
         - 하위 타입은 사전조건을 강화하면 안 된다 (더 까다롭게 받으면 안 됨)
         - 하위 타입은 사후조건을 약화하면 안 된다 (약속한 결과를 덜 주면 안 됨)
         - 하위 타입은 상위 타입의 불변식을 유지해야 한다

실행 방법
    python3 chapter_03_lsp.py
"""

from abc import ABC, abstractmethod


# ======================================================================
# 나쁜 코드: "모든 새는 난다"는 계약을 가진 Bird 를 펭귄이 상속한다
# ======================================================================

class BadBird(ABC):
    """모든 새의 상위 타입. fly() 의 계약을 문서로 약속한다.

    fly(altitude) 의 계약
        사전조건: altitude 는 0 보다 큰 정수이기만 하면 된다.
        사후조건: 호출이 끝나면 self.altitude == altitude 이다 (요청한 고도에 도달).
        불변식  : self.altitude 는 언제나 0 이상이다.
    """

    def __init__(self, name: str) -> None:
        self.name = name
        self.altitude = 0  # 불변식: 0 이상

    @abstractmethod
    def fly(self, altitude: int) -> None: ...


class BadSparrow(BadBird):
    """참새: 계약을 그대로 지킨다. 이것이 '정상적인 하위 타입'의 모습."""

    def fly(self, altitude: int) -> None:
        if altitude <= 0:
            raise ValueError("고도는 0보다 커야 합니다")  # 부모와 같은 사전조건
        self.altitude = altitude                           # 사후조건 충족


class BadPenguin(BadBird):
    # [문제 1] 펭귄은 날 수 없으니 예외를 던진다.
    #   → 부모는 "altitude > 0 이면 된다"고 약속했는데, 펭귄은 사실상
    #     "어떤 값도 받지 않는다"로 사전조건을 무한히 '강화'했다.
    #   → Bird 를 믿고 fly() 를 부른 클라이언트는 아무 잘못 없이 터진다.
    def fly(self, altitude: int) -> None:
        raise NotImplementedError(f"{self.name}: 펭귄은 날 수 없습니다")


class BadOstrich(BadBird):
    # [문제 2] 타조는 예외 대신 '조용히 아무것도 안 한다'.
    #   → 에러가 안 나니 더 위험하다. 호출 후 altitude 가 여전히 0 이므로
    #     "요청 고도에 도달한다"는 사후조건을 '약화'한 것이다.
    #   → 버그가 호출 지점이 아니라 한참 뒤(고도 계산, 통계 등)에서 드러난다.
    def fly(self, altitude: int) -> None:
        pass


class BadHummingbird(BadBird):
    # [문제 3] 벌새는 날지만 "10m 이하만 가능"이라는 조건을 추가했다.
    #   → 부모보다 '더 까다로운 입력'을 요구 = 사전조건 강화.
    #   → 날 수 있는 새라도 계약을 바꾸면 LSP 위반이다. (날기 여부만의 문제가 아님!)
    def fly(self, altitude: int) -> None:
        if not 0 < altitude <= 10:
            raise ValueError(f"{self.name}: 10m 이하로만 날 수 있습니다")
        self.altitude = altitude


def bad_migrate(birds: list[BadBird], altitude: int) -> list[str]:
    """철새 이동 시뮬레이션: Bird 타입만 보고 모두 fly(altitude) 를 부른다."""
    report: list[str] = []
    for bird in birds:
        # [문제 4] 하위 타입이 계약을 깨니, 클라이언트가 '타입 검사'로 방어하기 시작한다.
        #   → 새로운 '못 나는 새'(키위, 도도…)가 추가될 때마다 이 줄을 고쳐야 한다.
        #   → 이 isinstance 사다리는 LSP 위반의 대표적인 냄새이며, OCP 까지 함께 깨뜨린다.
        if isinstance(bird, BadPenguin):
            report.append(f"{bird.name}: (펭귄은 건너뜀)")
            continue
        try:
            bird.fly(altitude)
        except (NotImplementedError, ValueError) as e:
            report.append(f"[예외] {e}")
            continue
        # [문제 2]의 결과: 예외가 없어도 사후조건이 깨졌는지 확인해야 하는 처지가 된다.
        ok = bird.altitude == altitude
        report.append(f"{bird.name}: 고도 {bird.altitude}m {'OK' if ok else '<- 사후조건 위반!'}")
    return report
번호무엇이 깨졌나계약 관점
[문제 1] 펭귄fly()가 항상 예외사전조건 강화: "altitude>0이면 된다" → "어떤 입력도 안 된다"
[문제 2] 타조fly()가 아무것도 안 함사후조건 약화: 요청 고도에 도달한다는 보장을 지키지 않음. 예외가 없어 더 늦게 발견됨
[문제 3] 벌새10m 초과 요청 거절사전조건 강화: 날 수 있는 새도 입력 범위를 좁히면 위반
[문제 4] 클라이언트isinstance 사다리위반의 증상. 새 하위 타입마다 클라이언트를 고쳐야 함(OCP도 함께 깨짐)

⚠️ 흔한 오해

"NotImplementedError를 던지면 정직한 거니까 괜찮다"—아닙니다. 상위 타입이 "호출할 수 있다"고 약속한 메서드를 하위 타입이 거절하는 순간, 그 하위 타입은 상위 타입 자리에 들어갈 수 없습니다.

개선 코드

핵심 아이디어: "난다"는 약속을, 그 약속을 지킬 수 있는 새들에게만 요구합니다. Bird에는 모든 새가 지킬 수 있는 계약(eat, move)만 남기고, fly 계약은 FlyingBird로 옮깁니다.

# ======================================================================
# 개선 코드: '날 수 있음'을 별도 타입으로 분리해 계약을 지킬 수 있는 자만 약속한다
# ======================================================================

class Bird(ABC):
    """모든 새가 '정말로' 지킬 수 있는 것만 약속하는 상위 타입.

    [해결 1] '난다'는 약속을 여기서 뺐다.
        모든 새가 지킬 수 있는 계약(먹기, 이동하기)만 남기면
        어떤 하위 타입도 계약을 깰 이유가 사라진다.

    move() 의 계약
        사전조건: distance 는 0 보다 크다.
        사후조건: 반환값은 '어떻게 이동했는지'를 설명하는 비어 있지 않은 문자열이다.
    """

    def __init__(self, name: str) -> None:
        self.name = name

    def eat(self) -> str:
        return f"{self.name}: 먹이를 먹는다"

    @abstractmethod
    def move(self, distance: int) -> str: ...


class FlyingBird(Bird):
    """'날 수 있는 새'만의 상위 타입. fly() 계약은 여기서 약속한다.

    [해결 2] fly() 계약을 '지킬 수 있는 새들'에게만 요구한다.
    fly(altitude) 의 계약
        사전조건: altitude > 0  (하위 타입이 이보다 까다롭게 받으면 안 된다)
        사후조건: 호출 후 self.altitude == altitude
        불변식  : self.altitude >= 0
    """

    def __init__(self, name: str) -> None:
        super().__init__(name)
        self.altitude = 0

    def fly(self, altitude: int) -> None:
        # [해결 3] 사전조건 검사를 상위 타입에 한 번만 둔다.
        #   하위 타입은 _ascend() 만 구현하므로, 실수로 사전조건을 강화할 여지가 줄어든다.
        if altitude <= 0:
            raise ValueError("고도는 0보다 커야 합니다")
        self._ascend(altitude)
        # 사후조건을 코드로 확인(assert)해 두면, 계약을 깨는 하위 타입이 즉시 드러난다.
        assert self.altitude == altitude, f"{self.name}: fly 사후조건 위반"

    def _ascend(self, altitude: int) -> None:
        """기본 구현: 요청 고도로 올라간다. 하위 타입은 '방법'만 바꿀 수 있다."""
        self.altitude = altitude

    def move(self, distance: int) -> str:
        return f"{self.name}: {distance}km 를 날아서 이동"


class Sparrow(FlyingBird):
    pass  # 부모 계약을 그대로 따른다.


class Eagle(FlyingBird):
    # [해결 4] 사후조건을 '강화'하는 것은 허용된다.
    #   요청 고도에 도달한다는 약속은 지키면서, 추가로 '활공 로그'를 남긴다.
    #   (더 많이 주는 것은 괜찮고, 덜 주는 것이 위반이다.)
    def _ascend(self, altitude: int) -> None:
        self.altitude = altitude
        self.glide_log = f"{altitude}m 에서 활공 중"


class Hummingbird(FlyingBird):
    # ([문제 3]의 벌새) "10m 이하만" 같은 사전조건을 더하지 않는다.
    #   날갯짓 방식(정지 비행)은 _ascend() 안에서 바꾸되, 요청 고도에는 도달한다.
    #   고도 제한이 '진짜 요구'라면 하위 타입이 몰래 거절할 것이 아니라
    #   FlyingBird 계약 자체에 최대 고도를 명시해야 한다(모든 클라이언트가 알도록).
    def _ascend(self, altitude: int) -> None:
        self.altitude = altitude
        self.hover = True  # 방법은 달라도 계약(사후조건)은 그대로 지킨다


class Penguin(Bird):
    # [해결 5] 펭귄은 FlyingBird 가 아니므로 fly() 자체가 없다.
    #   '못 하는 일을 예외로 거절'하는 대신, 애초에 약속하지 않는다.
    def move(self, distance: int) -> str:
        return f"{self.name}: {distance}km 를 헤엄쳐서 이동"

    def swim(self) -> str:
        return f"{self.name}: 물속을 헤엄친다"


class Ostrich(Bird):
    def move(self, distance: int) -> str:
        return f"{self.name}: {distance}km 를 달려서 이동"


def migrate(birds: list[FlyingBird], altitude: int) -> list[str]:
    # [해결 6] 클라이언트는 FlyingBird 만 받는다. isinstance 사다리가 사라졌다.
    #   어떤 FlyingBird 하위 타입이 들어와도 fly() 계약이 지켜지므로 그냥 믿고 부른다.
    report: list[str] = []
    for bird in birds:
        bird.fly(altitude)
        report.append(f"{bird.name}: 고도 {bird.altitude}m OK")
    return report


def travel(birds: list[Bird], distance: int) -> list[str]:
    # [해결 7] 모든 새에게 공통으로 시킬 일은 Bird 의 계약(move)만 사용한다.
    #   펭귄·타조·참새 무엇이 와도 치환 가능하다.
    return [bird.move(distance) for bird in birds]


# ----------------------------------------------------------------------
# 요구 변경: "키위(못 남)와 매(남)를 추가해 주세요"
#   - 나쁜 코드: bad_migrate 의 isinstance 검사에 키위를 추가해야 한다(클라이언트 수정).
#   - 개선 코드: 아래 두 클래스만 추가하면 끝. migrate/travel 은 한 줄도 안 바뀐다.
# ----------------------------------------------------------------------

class Kiwi(Bird):
    def move(self, distance: int) -> str:
        return f"{self.name}: {distance}km 를 종종걸음으로 이동"


class Falcon(FlyingBird):
    pass


if __name__ == "__main__":
    print("=== 나쁜 코드: Bird 자리에 하위 타입을 넣으면 ===")
    bad_birds: list[BadBird] = [
        BadSparrow("참새"),
        BadPenguin("펭귄"),
        BadOstrich("타조"),
        BadHummingbird("벌새"),
    ]
    for line in bad_migrate(bad_birds, altitude=100):
        print(" ", line)

    # isinstance 로 펭귄만 막았기 때문에, 펭귄을 직접 부르면 여전히 터진다.
    try:
        BadPenguin("황제펭귄").fly(100)
    except NotImplementedError as e:
        print("  [직접 호출 시 예외]", e)

    print()
    print("=== 개선 코드: 계약을 지킬 수 있는 타입끼리 묶기 ===")
    flyers: list[FlyingBird] = [Sparrow("참새"), Eagle("독수리"), Hummingbird("벌새"), Falcon("매")]
    for line in migrate(flyers, altitude=100):
        print(" ", line)

    everyone: list[Bird] = [Sparrow("참새"), Penguin("펭귄"), Ostrich("타조"), Kiwi("키위")]
    for line in travel(everyone, distance=5):
        print(" ", line)

    # 정적 타입 검사기(mypy 등)라면 migrate([Penguin("펭귄")], 100) 을
    # '실행 전에' 타입 오류로 잡아 준다. 계약 위반이 런타임 사고가 아니라 설계 단계에서 막힌다.
    print("  펭귄에게 fly 가 있나?", hasattr(Penguin("펭귄"), "fly"))

같은 요구 변경을 이제 어떻게 흡수하나

"키위(못 남)와 매(남)를 추가해 주세요" → Kiwi(Bird), Falcon(FlyingBird) 두 클래스만 추가합니다. migrate()와 travel()은 한 줄도 바뀌지 않습니다. 펭귄을 migrate()에 넘기는 실수는 mypy 같은 정적 타입 검사기가 실행 전에 잡아 줍니다.

[문제 3]의 벌새는 Hummingbird(FlyingBird)로 다시 들어옵니다. 이번에는 "10m 이하만"이라는 조건을 붙이지 않고, 정지 비행이라는 방법만 _ascend()에서 바꾼 채 요청 고도에 도달한다는 계약을 지킵니다. 만약 고도 제한이 정말 필요한 요구라면, 하위 타입이 몰래 거절할 것이 아니라 FlyingBird 계약 자체에 최대 고도를 적어 모든 클라이언트가 알게 해야 합니다.

📦 새 개념: 정적 타입 검사기 (mypy)

  • 정의: 코드를 실행하지 않고 타입 힌트만 읽어 타입이 맞지 않는 호출을 찾아 주는 도구. mypy가 대표적이다(pip install mypy 후 mypy 파일.py)
  • 왜 필요?: 파이썬은 타입 힌트를 실행 중에 검사하지 않는다. 계약 위반을 실행 전에 잡으려면 검사기가 필요하다
  • 예: migrate([Penguin("펭귄")], 100) → mypy가 "list[Penguin]은 list[FlyingBird]가 아니다"라고 표시

⚠️ 흔한 오해

  • "LSP = 오버라이드 금지": 아닙니다. 계약 안에서 방법을 바꾸는 것(Eagle._ascend)은 자유입니다.
  • "메서드 시그니처만 같으면 치환 가능": 시그니처는 같아도 벌새처럼 동작의 약속을 바꾸면 위반입니다.
  • "is-a 관계면 상속해도 된다": 현실의 분류("펭귄은 새다")만으로는 부족합니다. 코드에서 is-a는 "상위 타입의 계약을 지킨다"는 행위의 is-a여야 합니다.

💡 과잉 적용 주의

"혹시 모르니" FlyingBird, SwimmingBird, RunningBird, NightFlyingBird…처럼 능력마다 계층을 미리 쪼개지 마세요. 계약을 실제로 깨는 하위 타입이 등장했을 때, 그 계약을 쓰는 클라이언트가 실제로 있을 때 나누면 됩니다. 능력 조합이 많아지면 상속 대신 다음 장의 작은 인터페이스(ISP)나 조합(composition)을 검토하세요.

이해 점검

Q1. [개념 확인] (학습목표 1)

LSP를 계약 관점에서 가장 정확하게 표현한 것은?

  1. 하위 클래스는 상위 클래스의 메서드를 오버라이드하면 안 된다.
  2. 현실에서 "A는 B의 일종"이면 A는 B를 상속해야 한다.
  3. 하위 타입은 사전조건을 강화하지 않고, 사후조건을 약화하지 않으며, 불변식을 유지해야 한다.
  4. 하위 타입은 상위 타입과 메서드 이름·매개변수가 같기만 하면 된다.
정답: 3
LSP는 "상위 타입의 계약을 그대로 지켜 치환 가능해야 한다"는 원칙이고, 그 판정 기준이 사전조건·사후조건·불변식입니다.
왜 오답이 매력적인가: 1은 "LSP = 바꾸지 마라"로 오해하기 쉬워서 끌리지만, 계약 안에서 방법을 바꾸는 오버라이드는 허용됩니다. 2는 펭귄 예처럼 is-a가 맞아도 계약을 못 지키면 위반입니다. 4는 시그니처 일치만으로는 벌새처럼 동작 약속을 바꾸는 위반을 걸러내지 못합니다.

Q2. [개념 확인] (학습목표 1)

상위 타입의 fly(altitude)는 "altitude > 0"을 받는다. 하위 타입이 "0 < altitude ≤ 10만 받는다"로 입력을 더 엄격하게 검사하는 것은 더 안전한 구현이므로 LSP를 지킨 것이다.

  1. O
  2. X
정답: X
입력을 더 엄격하게 받는 것은 사전조건 강화입니다. 상위 타입만 믿고 fly(100)을 부른 클라이언트가 이유 없이 실패하므로 치환할 수 없습니다(본문의 벌새, [문제 3]).
왜 O가 매력적인가: "검사를 더 하면 안전하다"는 직관 때문입니다. 하지만 안전은 자기 자신에게만 해당하고, 상위 타입의 약속을 믿은 호출자에게는 계약 파기입니다. 반대로 사전조건을 완화(더 너그럽게 받기)하는 것은 허용됩니다.

Q3. [위반 찾기] (학습목표 2)

새장 관리 코드입니다. Cage의 계약은 "add() 후 count()는 정확히 1 증가한다"입니다. LSP를 위반하는 클래스는?

class Cage:
    def __init__(self) -> None:
        self.birds: list[str] = []
    def add(self, name: str) -> None:
        self.birds.append(name)
    def count(self) -> int:
        return len(self.birds)

class LoggedCage(Cage):          # (가)
    def add(self, name: str) -> None:
        print(f"입실: {name}")
        super().add(name)

class SmallCage(Cage):           # (나)
    def add(self, name: str) -> None:
        if self.count() < 3:
            super().add(name)    # 3마리가 차면(4번째부터) 조용히 무시

class TaggedCage(Cage):          # (다)
    def add(self, name: str) -> None:
        super().add(name.strip().title())
  1. (가) LoggedCage
  2. (나) SmallCage
  3. (다) TaggedCage
  4. 위반하는 클래스가 없다
정답: 2
(나)는 4번째 새부터 add()를 조용히 무시해 "count가 1 증가한다"는 사후조건을 약화합니다. 예외도 없어서 본문의 타조([문제 2])처럼 버그가 늦게 드러납니다.
왜 오답이 매력적인가: (가)는 출력이라는 부수 동작을 더했지만 사후조건은 그대로 지키므로 괜찮습니다(추가 보장은 허용). (다)는 이름을 정규화할 뿐 개수 증가 약속은 지킵니다—"동작을 바꿨다 = 위반"이라고 착각하기 쉽습니다. 4를 고른 경우, 예외가 안 나면 괜찮다고 본 것일 수 있습니다.

Q4. [리팩터링 실습] (학습목표 3)

Q3의 SmallCage가 "최대 3마리"라는 요구를 유지하면서도 LSP를 지키도록 설계를 바꿔 보세요. (힌트: 계약을 상위 타입에서 정직하게 표현하거나, 상속 관계를 끊는 두 방향이 있습니다.)

모범 답안 예시 
class CageFullError(Exception): ...

class Cage:
    """add 계약: 사전조건 is_full()이 False. 사후조건 count()가 1 증가.
    is_full()이 True일 때 add하면 CageFullError."""
    capacity: int | None = None   # None = 무제한

    def __init__(self) -> None:
        self.birds: list[str] = []
    def is_full(self) -> bool:
        return self.capacity is not None and len(self.birds) >= self.capacity
    def add(self, name: str) -> None:
        if self.is_full():
            raise CageFullError(name)
        self.birds.append(name)

class SmallCage(Cage):
    capacity = 3   # 계약은 그대로, 값만 다르다
핵심: "가득 찰 수 있다"는 사실을 상위 타입의 계약에 포함시켜, 모든 클라이언트가 is_full()을 확인하거나 CageFullError를 처리하도록 약속합니다. 그러면 SmallCage는 새 조건을 몰래 추가하는 것이 아니라 같은 계약 안에서 값만 바꾼 것이 됩니다. 다른 방향: 용량 제한 우리를 Cage의 하위 타입이 아닌 별도 클래스로 두고, 무제한 추가가 필요한 클라이언트에는 넘기지 않습니다.
흔한 오답: SmallCage.add에서 예외만 던지도록 바꾸기. 조용한 무시보다는 낫지만, 상위 타입 계약에 없는 실패이므로 여전히 사전조건 강화입니다.

Q5. [서술형] (학습목표 1, 3)

동료가 "펭귄도 생물학적으로 새인데, Bird에서 fly를 빼고 FlyingBird를 따로 만드는 건 현실을 왜곡하는 것 아니냐"고 묻습니다. LSP 관점에서 답하고, 이 분리를 하지 않아도 되는 경우도 하나 제시하세요.

채점 포인트
  • 타입 계층은 생물 분류가 아니라 코드가 믿는 약속(계약)을 표현한다. Bird가 "날 수 있다"를 약속하면 펭귄은 그 약속을 지킬 수 없으므로 치환 불가능하다.
  • 분리하지 않으면 클라이언트에 isinstance 검사가 퍼지고, 새 종이 추가될 때마다 클라이언트를 고쳐야 한다(OCP 위반으로 번짐).
  • 분리하지 않아도 되는 경우: 시스템에 fly()를 호출하는 클라이언트가 아예 없거나(예: 조류 도감 앱이 이름·서식지만 보여줌), 날지 못하는 새가 등장할 가능성이 실제로 없을 때. 계약이 없으면 깨질 계약도 없으므로 미리 계층을 쪼개는 것은 과잉 설계다.
왜 헷갈리는가: 학교에서 상속을 "is-a 관계"로 배우기 때문에 현실 분류가 곧 정답 계층이라고 생각하기 쉽습니다.
