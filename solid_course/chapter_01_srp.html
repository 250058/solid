01. SRP 단일 책임 원칙

Single Responsibility Principle — "한 클래스는 한 가지 이유로만 바뀌어야 한다." 카페 주문서 예제로 '책임'이 정확히 무엇인지 알아봅니다.

학습목표

  1. SRP의 '책임'을 "변경 이유"로 정의하고, "메서드 하나 = 책임 하나"라는 오해를 구별할 수 있다.
  2. 주어진 클래스에서 서로 다른 변경 이유(누가, 왜 고치러 오는가)를 찾아낼 수 있다.
  3. 여러 책임이 섞인 클래스를 변경 이유별 클래스로 분리할 수 있다.

개념

한 문장 정의: 클래스(모듈)는 변경 이유가 단 하나여야 한다.

왜 필요할까요? 한 클래스에 여러 변경 이유가 섞여 있으면, A 요구 때문에 고친 코드가 전혀 상관없는 B 기능을 망가뜨릴 수 있습니다. 또 서로 다른 사람(부서)이 같은 파일을 동시에 고치면서 충돌이 납니다.

📦 새 개념: 책임 = 변경 이유

  • 정의: SRP에서 '책임'은 "하는 일의 개수"가 아니라 "이 코드를 바꾸라고 요구할 수 있는 이유(또는 그 요구를 하는 사람·부서)"이다
  • 왜 필요?: "일 하나"는 얼마든지 잘게 쪼갤 수 있어 기준이 모호하다. "누가 왜 고치러 오는가"는 판단 기준이 분명하다
  • 예: 가격 계산(사장님·회계), 영수증 모양(매장 디자인), 저장 방식(개발·인프라) → 변경 이유 3개 = 책임 3개

📦 새 개념: 관심사 분리 (Separation of Concerns)

  • 정의: 프로그램을 서로 다른 관심사(계산, 표시, 저장 등)별로 나누어, 각 부분이 자기 관심사만 다루게 하는 설계 원리
  • 왜 필요?: 한 관심사의 변화가 다른 관심사로 번지지 않게 막고, 각 부분을 따로 이해·테스트할 수 있게 한다
  • 예: 웹의 HTML(구조)/CSS(모양)/JS(동작) 분리, 이번 장의 Order/ReceiptPrinter/OrderRepository

SRP는 관심사 분리를 "클래스 단위"에서 "변경 이유"라는 잣대로 적용한 것이라고 볼 수 있습니다.

상황

동네 카페의 주문 프로그램입니다. CafeOrder 클래스 하나가 메뉴 담기, 합계 계산, 영수증 출력, 주문 파일 저장을 모두 합니다. 처음엔 편했습니다.

그런데 한 주 동안 이런 요구가 연달아 들어옵니다.

  • 사장님: "텀블러 가져오면 300원 깎아 주세요." (가격 정책)
  • 매장 직원: "영수증 맨 밑에 와이파이 비밀번호 좀 찍어 주세요." (출력 모양)
  • 개발 담당: "주문이 늘어서 파일 대신 DB에 저장해야 해요." (저장 방식)

세 요구 모두 CafeOrder 한 파일을 고쳐야 합니다. 영수증 문구를 고치다 실수로 합계 계산을 건드리면, 손님에게 돈을 잘못 받게 됩니다.

나쁜 코드

파일 상단(설명과 import)입니다.

"""01장. SRP 단일 책임 원칙 — 카페 주문서

목적
    주문 계산, 영수증 출력, 파일 저장을 모두 떠안은 클래스를
    '변경 이유' 기준으로 나누어 보고, 요구사항이 바뀔 때
    어느 클래스만 고치면 되는지 확인한다.

다루는 원칙
    SRP(Single Responsibility Principle):
    "클래스(모듈)는 변경 이유가 단 하나여야 한다."

실행 방법
    python3 chapter_01_srp.py
    (데모는 임시 폴더에 주문 파일을 저장했다가 지운다.)
"""
from __future__ import annotations

import json
import tempfile
from dataclasses import dataclass, field
from pathlib import Path
# ===== 나쁜 코드: 계산·출력·저장을 한 클래스가 모두 담당 =====

class CafeOrder:
    """주문에 관한 모든 일을 혼자 하는 '만능' 클래스."""

    def __init__(self, customer: str) -> None:
        self.customer = customer
        self.items: list[tuple[str, int, int]] = []  # (메뉴, 단가, 수량)

    def add_item(self, name: str, price: int, qty: int = 1) -> None:
        self.items.append((name, price, qty))

    # [문제 1] 변경 이유 ①: 가격 정책(사장님/회계).
    #          "텀블러 지참 시 300원 할인"이 생기면 이 메서드를 고친다.
    def total(self) -> int:
        return sum(price * qty for _, price, qty in self.items)

    # [문제 2] 변경 이유 ②: 영수증 모양(디자이너/매장 직원).
    #          "영수증 끝에 와이파이 비밀번호 출력" 요구가 오면
    #          계산 로직과 같은 클래스를 열어 고쳐야 한다.
    def print_receipt(self) -> str:
        lines = [f"[영수증] {self.customer}님"]
        for name, price, qty in self.items:
            lines.append(f"  {name} x{qty}  {price * qty:,}원")
        lines.append(f"  합계: {self.total():,}원")
        return "\n".join(lines)

    # [문제 3] 변경 이유 ③: 저장 방식(개발/인프라).
    #          "파일 말고 DB에 저장" 요구가 오면 또 이 클래스를 고친다.
    #          게다가 저장 형식을 바꾸다 실수하면 계산·출력까지 망가질 위험이 있다.
    def save(self, path: Path) -> None:
        data = {"customer": self.customer, "items": self.items, "total": self.total()}
        path.write_text(json.dumps(data, ensure_ascii=False), encoding="utf-8")

    # [문제 4] 결과: 세 부서의 요구가 한 파일에서 충돌한다.
    #          계산만 테스트하고 싶어도 파일 저장 코드까지 함께 딸려 온다.
  • [문제 1~3] 메서드 이름만 보면 깔끔해 보이지만, 각 메서드를 고치러 오는 사람이 모두 다릅니다. 변경 이유가 3개입니다.
  • [문제 4] 계산 로직만 테스트하고 싶어도 저장 코드(파일 시스템)와 한 덩어리로 묶여 있습니다.

⚠️ 흔한 오해: "메서드가 하나씩 나뉘어 있으니 SRP를 지킨 것 아닌가요?"

아닙니다. SRP의 단위는 메서드가 아니라 클래스(모듈)이고, 기준은 메서드 개수가 아니라 변경 이유입니다. total, print_receipt, save가 각각 한 가지 일을 해도, 한 클래스에 서로 다른 변경 이유 3개가 모여 있으면 SRP 위반입니다.

개선 코드

# ===== 개선 코드: 변경 이유별로 클래스를 분리 =====

# [해결 1] Order: 주문 '데이터와 가격 계산'만 책임진다.
#          변경 이유는 오직 "가격 정책이 바뀔 때" 하나.
@dataclass
class OrderItem:
    name: str
    price: int
    qty: int = 1


@dataclass
class Order:
    customer: str
    items: list[OrderItem] = field(default_factory=list)

    def add_item(self, name: str, price: int, qty: int = 1) -> None:
        self.items.append(OrderItem(name, price, qty))

    def total(self) -> int:
        return sum(item.price * item.qty for item in self.items)


# [해결 2] ReceiptPrinter: '영수증 모양'만 책임진다.
#          와이파이 비밀번호 줄을 추가하려면 여기만 고치면 되고,
#          Order의 계산 로직은 건드리지 않는다.
class ReceiptPrinter:
    def __init__(self, footer: str = "") -> None:
        self.footer = footer

    def render(self, order: Order) -> str:
        lines = [f"[영수증] {order.customer}님"]
        for item in order.items:
            lines.append(f"  {item.name} x{item.qty}  {item.price * item.qty:,}원")
        lines.append(f"  합계: {order.total():,}원")  # 계산은 Order에게 '맡긴다'
        if self.footer:
            lines.append(f"  {self.footer}")
        return "\n".join(lines)


# [해결 3] OrderRepository: '저장 방식'만 책임진다.
#          DB로 바꿔야 하면 이 클래스만 교체한다. Order와 ReceiptPrinter는 무사하다.
class OrderRepository:
    def __init__(self, folder: Path) -> None:
        self.folder = folder

    def save(self, order: Order) -> Path:
        path = self.folder / f"order_{order.customer}.json"
        data = {
            "customer": order.customer,
            "items": [vars(item) for item in order.items],
            "total": order.total(),
        }
        path.write_text(json.dumps(data, ensure_ascii=False), encoding="utf-8")
        return path


# [해결 4] 관심사 분리의 효과: 각 클래스를 따로 테스트할 수 있다.
#          예) Order.total()은 파일 시스템 없이도 검증 가능하다.

이제 같은 세 요구가 오면 어디를 고칠까요?

요구고치는 곳안전한 곳
텀블러 300원 할인OrderReceiptPrinter, OrderRepository
영수증에 와이파이 비밀번호ReceiptPrinter (데모처럼 footer로 해결)Order, OrderRepository
파일 → DB 저장OrderRepository (또는 새 저장소 클래스)Order, ReceiptPrinter

        printer = ReceiptPrinter(footer="Wi-Fi: cafe1234")

        assert order.total() == 15000  # 계산만 독립적으로 검증

📦 새 개념: assert 문

  • 정의: assert 조건, "메시지" — 조건이 거짓이면 그 자리에서 AssertionError를 던지는 문장
  • 왜 필요?: "여기서는 반드시 이래야 한다"는 사후조건·불변식을 코드로 확인해, 계약을 깨는 코드를 즉시 드러내려고
  • 주의: python -O로 실행하면 assert가 모두 꺼진다. 사용자 입력 검사(사전조건)에는 쓰지 말고 raise ValueError를 쓴다

📦 새 개념: @dataclass / field(default_factory=...)

  • 정의: @dataclass는 필드 선언만 보고 __init__, __repr__, __eq__를 자동으로 만들어 주는 표준 라이브러리 데코레이터. field(default_factory=list)는 객체마다 새 빈 리스트를 기본값으로 만든다
  • 왜 필요?: 데이터 중심 클래스의 반복 코드를 줄이려고. 기본값을 = []로 쓰면 모든 객체가 리스트 하나를 공유하는 버그가 생기므로 default_factory를 쓴다
  • 예: items: list[OrderItem] = field(default_factory=list). @dataclass(frozen=True)로 쓰면 만든 뒤 값을 바꿀 수 없다(6장에서 사용)

💡 핵심 포인트

ReceiptPrinter와 OrderRepository는 Order를 사용하지만, 합계를 직접 계산하지 않고 order.total()에 맡깁니다. 그래서 가격 정책이 바뀌어도 이 둘은 영향을 받지 않습니다. 책임을 나눈다는 것은 "남의 일을 대신하지 않는다"는 뜻이기도 합니다.

관점나쁜 코드 (CafeOrder)개선 코드 (3개 클래스)

테스트계산 테스트에 파일 저장이 딸려 옴Order.total()만 독립 검증

⚠️ 흔한 오해와 과잉 적용 주의

  • "클래스엔 메서드가 하나만 있어야 한다" — 틀렸습니다. Order에는 add_item과 total이 있지만 둘 다 "가격·주문 규칙"이라는 같은 이유로 바뀝니다.
  • "잘게 쪼갤수록 좋다" — AmericanoPriceCalculator, LattePriceCalculator처럼 같은 이유로 함께 바뀌는 것을 쪼개면 오히려 한 번의 변경에 여러 파일을 고쳐야 합니다(응집도↓).
  • 판단 질문: "이 두 코드는 같은 사람이, 같은 이유로, 같은 시점에 고치러 오는가?" — 그렇다면 함께 두고, 아니라면 나누세요.

이해 점검

Q1. [개념 확인] (학습목표 1)

SRP에서 말하는 "책임"의 의미로 가장 정확한 것은?

  1. 클래스가 가진 메서드 하나하나
  2. 클래스가 처리하는 데이터의 종류
  3. 그 클래스를 변경하게 만드는 이유
  4. 클래스의 코드 줄 수 한도
정답: 3번
SRP의 책임은 "변경 이유"입니다. 누가, 어떤 요구로 이 코드를 고치러 오는지가 기준입니다.
왜 1번이 매력적인가? "단일 책임"이라는 이름 때문에 "일 하나 = 메서드 하나"로 오해하기 쉽습니다. 하지만 같은 이유로 함께 바뀌는 메서드 여러 개는 한 클래스에 있는 것이 자연스럽습니다.

Q2. [개념 확인] (학습목표 1)

"Order 클래스에 add_item과 total 두 메서드가 있으므로 SRP를 위반한다." (O/X)

  1. O
  2. X
정답: X
두 메서드는 모두 "주문·가격 규칙"이 바뀔 때만 바뀝니다. 변경 이유가 하나이므로 SRP를 지킵니다.
왜 O가 매력적인가? 메서드 개수를 세는 습관 때문입니다. 개수가 아니라 변경 이유를 세야 합니다.

Q3. [위반 찾기] (학습목표 2)

카페의 직원 관리 클래스입니다. 서로 다른 변경 이유는 모두 몇 개인가요?

class Barista:
    def calc_pay(self) -> int: ...          # 시급 × 근무시간 (급여 규정)
    def calc_overtime(self) -> int: ...     # 야간 수당 계산 (급여 규정)
    def to_schedule_html(self) -> str: ...  # 근무표 웹 화면 (화면 디자인)
    def save_to_db(self) -> None: ...       # DB 저장 (저장 방식)
  1. 1개
  2. 2개
  3. 3개
  4. 4개
정답: 3번(3개)
급여 규정(calc_pay, calc_overtime), 화면 디자인(to_schedule_html), 저장 방식(save_to_db) — 변경 이유는 3개입니다. 급여 두 메서드는 같은 이유로 바뀌므로 하나로 셉니다.
왜 4번(4개)이 매력적인가? 메서드 수를 그대로 세면 4가 나옵니다. "급여 규정이 바뀌면 둘 다 함께 바뀐다"는 점을 놓친 것입니다.

Q4. [리팩터링 실습] (학습목표 3)

Q3의 Barista 클래스를 SRP에 맞게 나누어 보세요. 클래스 이름과 각 클래스가 담당하는 메서드, 그리고 "근무표를 PDF로도 뽑아 달라"는 요구가 왔을 때 고치는 클래스를 적으세요.

예시 답안 
class Barista:                 # 직원 데이터 + 급여 규정 (변경 이유: 급여 규정)
    def calc_pay(self) -> int: ...
    def calc_overtime(self) -> int: ...

class ScheduleView:            # 근무표 표시 (변경 이유: 화면/출력 형식)
    def to_html(self, barista: Barista) -> str: ...

class BaristaRepository:       # 저장 (변경 이유: 저장 방식)
    def save(self, barista: Barista) -> None: ...
PDF 요구는 출력 형식의 변화이므로 ScheduleView 쪽(또는 새 SchedulePdfView)만 다룹니다. 급여 계산과 DB 저장은 건드리지 않습니다.
흔한 실수: calc_pay와 calc_overtime까지 따로 떼어 클래스를 4개로 만드는 것 — 같은 이유로 함께 바뀌므로 과잉 분리입니다.

Q5. [서술형] (학습목표 1, 3)

친구가 "SRP를 지키려고 모든 클래스에 메서드를 하나씩만 두었어"라고 합니다. 이 방식의 문제를 '변경 이유'와 '응집도'라는 말을 써서 2~3문장으로 설명하세요.

모범 답안 요지: SRP의 기준은 메서드 개수가 아니라 변경 이유입니다. 같은 이유로 함께 바뀌는 메서드를 여러 클래스에 흩어 놓으면 한 번의 요구 변경에 여러 파일을 고쳐야 하고, 관련 코드가 흩어져 응집도가 떨어집니다. 따라서 "같은 이유로 바뀌는 것은 모으고, 다른 이유로 바뀌는 것은 나누는" 것이 올바른 적용입니다.
채점 포인트: ① 기준=변경 이유 ② 과잉 분리 → 응집도 하락 ③ 모으기/나누기 기준 제시.
